# 레이턴시 리팩토링 (2026-09-13)

워커 응답이 느리다는 문제로 시작했다. 목표는 하나다 — **프론트(momote.site)·백엔드에
주는 것은 한 글자도 바꾸지 않고, 워커 안에서만 시간을 줄인다.** 판정 규칙·프롬프트·
LLM 이 보는 입력도 안 바꿨다. 바뀐 것은 **언제 부르느냐**와 **이미 아는 것을 다시 묻지
않는 것**뿐이다.

| | |
| --- | --- |
| 연동 규격 (`docs/contract.md`) | **변경 없음.** 요청·응답 JSON, 필드, 상태 코드 전부 그대로 |
| 서버 쪽 작업 | **없음.** 로그 한 줄에 `분절캐시=N/M` 이 붙는 것뿐 |
| 프론트 쪽 작업 | **없음** |
| 판정 규칙 · 프롬프트 · 모델 | **변경 없음** (`gpt-4.1-mini` 그대로) |
| 새 환경변수 | `KAKAPO_SEGMENT_CACHE` · `KAKAPO_SEGMENT_TAIL` · `KAKAPO_LLM_TIMEOUT` · `KAKAPO_SERVICE_TIER` — 전부 선택, 기본값으로 동작 |

배경: 이제 사용자마다 채팅방을 만들 수 있다 (방 여러 개). 워커 처리 시간은 방 수와
무관하게 요청 하나 기준이고, 방이 늘면 **동시 요청**이 는다 — 그 부분은 7장.

---

## 1. 어디서 시간이 새고 있었나

리팩토링 전 요청 하나의 임계 경로:

```
분절 LLM (창 30개 3~4초, 창 6개 1초)  ← 맨 앞에 혼자 서 있어 모든 단계가 기다린다
   └─ 상태 산출 1.6~2.4초  ∥  말투 판정 1.2 → 생성 1.1  ∥  기억 추출 0.6~1.5  ∥  데이트 계획 1.5 → 카카오 0.4 → 문구 1.4
```

세 가지가 보였다.

1. **분절이 매 요청 전량 재채점된다.** 백엔드는 메시지 1건마다 최근 창 30개를 통째로
   보낸다. 요청 N+1 에서 새로 온 발화는 한두 개인데 30개를 다시 채점하고 있었다.
   분절 출력이 발화 수에 비례하니(발화당 ~11토큰) 이게 그대로 지연이다.
2. **말투 후보가 분절을 기다릴 이유가 없다.** 판정·생성 프롬프트가 보는 대화는
   `ctx.context` 의 마지막 4개인데, 그건 전체 스트림의 마지막 4개와 항상 같다
   (활성 세그먼트를 앞 세그먼트로 4개까지 채우기 때문). 분절 결과가 입력에 영향을 주지
   않는데 분절 뒤에 서 있었다.
3. **기억 추출이 응답을 잡고 있었다.** 추출 결과는 이번 요청의 결과에 쓰이지 않는다 —
   데이트 계획은 대화 원문을 프롬프트로 직접 받는다 (16단계에서 이미 확인). 저장은 다음
   요청을 위한 것인데 응답이 그걸 기다렸다.

## 2. 바꾼 것

### ① 분절 점수 캐시 — `worker/segment.py`

발화 하나의 점수는 "직전까지의 맥락과 얼마나 이어지는가"다. **같은 발화·같은 직전
발화면 재료가 같다.** 그래서 `(방, 발화 id)` 로 점수를 기억하고, 캐시에 없는 꼬리만
그 앞 전체를 '앞 맥락' 구획으로 붙여 채점한다. 분할 채점(`SCORE_BATCH`)의 배치 하나와
프롬프트 형식이 같아서 **LLM 이 보는 재료는 그대로고 출력만 준다.**

```
요청 N    [1 … 30]            30개 채점             3~4초
요청 N+1  [2 … 31]            캐시 28 + 채점 3      0.6~0.9초   ← 창 30개 기준
```

- **키에 내용 지문을 넣는다.** `(직전 id·내용, 이번 id·내용)` 의 해시가 다르면 다른
  발화다. 픽스처가 전부 `chatRoomId=1` 에 id 101~ 이 겹쳐서 이게 없으면 case7 의
  점수가 case9 에 붙는다.
- **꼬리 3개는 캐시가 있어도 다시 채점한다** (`SCORE_TAIL_MIN=3`). 새 발화 하나만
  채점 대상으로 주면 모델이 관대해진다 — 아래 검증 표. 출력 +22토큰이라 비용은 없다.
- **LRU 4,000 항목** (방 130개 × 창 30개). `KAKAPO_SEGMENT_CACHE=0` 이면 끈다.
- 로그 줄에 `분절캐시=N/M` 이 붙는다. 방의 첫 요청은 `0/M`, 그 뒤는 `M-3/M` 이 정상이다.

**무상태 원칙과의 관계.** 워커는 상태를 갖지 않는다는 원칙이 있다 (`recentResults` 를
서버가 실어주는 이유). 이 캐시는 **상태가 아니라 메모다** — 비어 있으면(재시작·다른
인스턴스·캐시 끔) 전부 다시 채점하고 결과 규칙은 하나도 안 바뀐다. 캐시 유무로 화면이
달라지는 경로가 없다.

**부수 효과가 좋은 쪽이다.** 같은 발화의 점수가 요청마다 안 흔들려서 세그먼트 경계가
안정된다. 유튜브·데이트의 "같은 화제엔 하나만" 억제가 세그먼트 시작 시각에 기대고
있어서, 경계가 흔들리면 억제가 새던 자리다 (`router.py` 의 `YOUTUBE_COOLDOWN_MIN`
주석에 "세그먼트 경계가 LLM 산출이라 흔들릴 때"라고 적어둔 바로 그 문제).

### ② 말투 후보 선행 실행 — `worker/router.run()`

분절 전에 **룰 컷만 적용한 마지막 조각**(`segment.rule_tail`, LLM 없이 즉시)으로 말투
게이트를 걸고, 걸리면 판정 → 생성 체인을 바로 시작한다. 분절이 끝나면 **활성 세그먼트로
게이트를 다시 계산해 신호가 같은지 확인**한다.

- 같으면 (거의 항상) 선행 결과를 채택한다.
- 다르면 버리고 정식으로 다시 돈다. 게이트 중 활성 세그먼트를 보는 건 `_repetition_flag`
  (화자의 직전 발화 3개)뿐이라, 그 3개 사이에 화제 경계가 걸릴 때만 다르다.
  다시 돌 때 트레이스에 "선행 실행 게이트가 활성 세그먼트와 달라 다시 판정"이 남는다.

어느 쪽이든 **LLM 이 보는 입력은 전과 동일하다** — 시점만 앞당긴다. 선행 실행은 자기
트레이스에 기록하고 채택될 때만 본 트레이스로 옮긴다 (버려진 실행이 늦게 끝나 덮어쓰는
경합 방지). 유튜브는 말투 결과를 기다리는데, 이제 분절이 끝날 때쯤 말투도 끝나 있어서
유튜브가 거의 바로 출발한다.

### ③ 기억 추출 백그라운드 — `router.run()` · `pipeline.analyze(wait_background)`

추출은 백그라운드 풀(4스레드)에 던지고 응답은 먼저 나간다. 다음 요청은 메시지 간격
(수초~수분) 뒤라 그때는 저장이 끝나 있다. 응답 시간에서 빠지는 것은 "추출이 상태
산출보다 길었던 만큼"(0~1초)이다.

- 서버(`worker/api.py`)는 안 기다린다 (기본값).
- CLI(`tools/run.py`)·devui 는 `wait_background=True` 로 기다려서 추출 결과를 그대로
  보여준다 — 화면·출력 형식 무변경.
- 예외는 로그로 남긴다. (전에도 `run()` 이 이 future 의 결과를 안 읽어서 예외가 조용히
  사라지고 있었다 — 이제 로그에는 남는다.)

### ④ `worker/llm.py` 소소한 것 셋

| | 무엇 | 왜 |
| --- | --- | --- |
| 구조화 러너블 캐시 | `with_structured_output(...)` 을 호출마다 새로 만들지 않는다 | pydantic JSON 스키마 생성이 단계 7종 × 요청마다 반복되던 순수 CPU 낭비 |
| `KAKAPO_LLM_TIMEOUT=15` | LLM 호출 하나의 HTTP 타임아웃 | 없으면 SDK 기본 **600초**. 연결이 멎으면 워커 마감 25초까지 통째로 기다렸다가 요청 전체가 `ANALYSIS_TIMEOUT`. 15초면 그 단계만 폴백(분절 → 안 자름, 상태 → 갱신 없음, 후보 → 미발동)으로 떨어지고 나머지는 산다 |
| `KAKAPO_SERVICE_TIER` | 비우면 기본. `priority` 면 OpenAI 우선 처리 | 선택 손잡이. 실측은 4장 |

### 되돌린 것 — `SCORE_BATCH` 15 → 10

배치를 줄이면 콜드 분절이 빨라진다(창 25개 1.9 → 1.5초). 그런데 **캐시 끄고 3회씩
재보니 배치가 작으면 경계를 잃는다** — case19(싸움 → 화해) `[10,4]` → `[14]` 3/3,
case21 의 `4·4` 가 `8` 로 합쳐짐 3/3. 채점 대상이 짧으면 모델이 낮은 점수를 안 준다.
15 로 되돌렸다. 캐시가 붙은 뒤로 배치 크기는 **방의 첫 요청**에서만 의미가 있다.

같은 현상이 캐시의 "새 발화 하나만 채점"에서도 나왔고(아래 3장), 그래서 꼬리 3개
재채점이 들어갔다.

## 3. 검증 — 결과가 안 바뀌었는가

### 경계 검증 (증분 요청 열)

백엔드와 같은 조건으로, 픽스처를 **메시지 하나씩 늘려가는 요청 열**로 돌려 마지막 창의
경계를 콜드 전량 채점과 비교했다. `SCORE_BATCH=15`.

| 픽스처 | 콜드 (캐시 없음) | 증분, 꼬리 1개 | 증분, 꼬리 3개 (채택) | 증분, 꼬리 5개 |
| --- | --- | --- | --- | --- |
| case11_mixed | `[5,3]` | `[5,3]` 2/2 | `[5,3]` 1/4, `[4,1,3]` 3/4 — 205("이따 얘기하자 나 바빠") 앞에 컷 하나 더. **활성 세그먼트·맥락은 동일** | `[5,3]` 4/4 |
| case19_washout | `[10,4]` | `[10,4]` 2/2 | `[10,4]` 4/4 | **`[14]` 4/4 — 경계 잃음** |
| case1_pingpong | `[10]` | `[10]` 4/4 | | |
| case3_one_sided | `[8]` | `[8]` 4/4 | | |
| case4_routine (룰 컷) | `[4,4,4]` | `[4,4,4]` 4/4 | | |
| **case2_no_question** | `[2,2,2,2]` 6/6 | **`[2,4,2]`·`[2,6]` — 3/4 무너짐** | `[2,2,2,2]` 4/4 | `[2,2,2,2]` 4/4 |
| case5_busy | `[4]` / `[1,3]` (콜드 자체가 흔들림) | `[1,3]` | 콜드와 3/4 일치 | 1/4 |
| case21_date_refire | `[13,…]` / `[9,4,…]` (콜드 자체가 흔들림) | 둘 중 하나 | 콜드와 3/4 일치 | 0/4 — 앞쪽이 잘게 쪼개짐 |

꼬리 1개는 case2 를, 5개는 case19 를 잃는다. **3개가 둘 다 지키고**, 어긋난 case11 은
활성 세그먼트(마지막 3개)와 말투 맥락이 그대로라 화면에 나가는 것이 안 바뀐다.

case2 가 문제였다. 2개짜리 소화제 4개가 이어지는 대화인데, **새 발화 하나만 채점
대상으로 주면 모델이 경계를 안 긋는다.** `SCORE_BATCH` 축소와 같은 현상이다 — 채점
대상이 몇 개 이어져야 앞뒤를 견주어 낮은 점수를 준다. 그래서 꼬리 3개는 캐시가 있어도
다시 채점하게 했다. 꼬리 개수별 결과는 4장 표.

### 오프라인 검증 (LLM 없이)

`_ask_scores` 를 가짜로 바꿔 호출 범위를 셌다 — 콜드 29개 2배치 / 슬라이딩 시 새 발화만
앞 맥락 29개 붙여 1회 / 다른 방 미적중 / 내용 변경 시 그 발화부터 재채점 / 캐시 끔 /
룰 컷 뒤 짧은 꼬리는 LLM 안 부름 / 선행 게이트 비교(신호 다르면 재실행). 15/15.

### 회귀

픽스처 21종을 CLI 로 돌려 `FAILED` 0, 발동 종류·상태 라벨이 리팩토링 전 벤치와 같다
(case19 의 `STABLE`/`ENGAGED`, 데이트 문구의 표현은 전에도 실행마다 흔들리던 편차다).

## 4. 실측 — 전후 (로컬, `gpt-4.1-mini`, 픽스처 2회씩)

`analyze()` 안쪽 벽시계다. 파이썬 기동·HTTP 는 빠져 있다. 숫자는 API 응답 편차가 ±0.5초
있으니 **줄어든 폭**으로 읽는다. "슬라이딩"은 case21(26개)에서 창 25개를 한 칸 밀어
두 요청을 연달아 보낸 것 — **배포에서 매 메시지마다 일어나는 조건**이다.

| 케이스 | 전 (2회) | 후 — 방의 첫 요청 | 후 — 이어지는 요청 (캐시 적중) |
| --- | --- | --- | --- |
| case8_banter (개입 없음) | 2.6 / 2.6 | 2.5 | **2.0** |
| case7_tone (말투) | 5.3 / 2.8 | 4.7 | **2.1** |
| case11_mixed (말투, 세그먼트 2) | 3.7 / 3.9 | 3.3 | **2.2** |
| case19_washout (14개, 개입 없음) | 3.6 / 3.9 | 3.8 | **1.6** |
| case21_date_refire (26개, 개입 없음) | 4.9 / 3.6 | 3.6 | **1.6** |
| case9_date (데이트) | 4.6 / 4.2 | 4.7 | **3.1** |
| case10_concern (유튜브, 시드) | 3.9 / 4.2 | 4.5 | **3.0** |
| **슬라이딩 창 25개 + 데이트** | 5.2 / 5.0 | — | **3.1 / 3.3 / 4.1** |

단계별로 보면:

| 단계 | 전 | 후 |
| --- | --- | --- |
| 분절 (창 25개) | 1.8~1.9초 (2배치, 출력 209+209) | **0.55~0.9초** (출력 ~33) |
| 분절 (창 6개) | 0.9~1.1초 | 0.6~0.8초 |
| 말투 판정+생성 | 분절 **뒤에** 2.3초 | 분절과 **겹쳐** — 말투 케이스에서 분절이 임계 경로에서 빠진다 |
| 기억 추출 | 0.6~1.5초, 응답이 기다림 | 응답 뒤에 돈다 |
| 상태 산출 | 1.6~2.4초 | 그대로 (16단계에서 못 줄인다고 확인한 자리) |
| 데이트 계획 → 카카오 → 문구 | 3.3초 | 그대로 (환각 방지 설계상 직렬) |

이제 임계 경로는 이렇다:

```
개입 없음   분절 0.6~0.9 → 상태 1.6~2.4                    ≈ 2.0~3.0초
말투        max(분절 → 상태, 판정 → 생성)                  ≈ 2.0~2.5초
데이트      분절 → 계획 → 카카오 → 문구                     ≈ 3.0~4.0초
유튜브      분절 → 분류 → 검색·댓글 → 선정                   ≈ 3.0초 (시드), 검색 시 +1초
```

### `service_tier=priority` (선택)

같은 벤치를 `KAKAPO_SERVICE_TIER=priority` 로 한 번 돌렸다. LLM 호출당 **25~30%**
빨라진다 — 상태 1.6~1.7 → 1.1~1.2초, 말투 판정·생성 각 0.7~0.8초, 데이트 체인 3.3 →
2.7초. 케이스 전체로는 case7 2.1 → 1.5초, case9 3.1 → 2.8초, 슬라이딩 데이트 3.1~4.1 →
2.7초. 토큰 단가가 오르므로(OpenAI 기준 표준의 2배) 기본은 꺼 두고 **시연·피크에만**
켠다. 켜고 끄는 데 코드 변경이 없다.

### 꼬리 재채점 개수 (`SCORE_TAIL_MIN`) — 3 으로 확정

경계 결과는 3장 표. 비용은 채점 대상당 ~11토큰이라 꼬리 3개면 출력 ~33토큰, 분절
호출 **0.8~1.0초**(창 25개 슬라이딩). 꼬리 3개로 다시 돌린 최종 벤치:

| 케이스 | 이어지는 요청 (캐시 적중) |
| --- | --- |
| case8_banter | 2.5 |
| case7_tone | 2.5 / 2.6 |
| case11_mixed | 2.4 |
| case21_date_refire | 2.4 |
| 슬라이딩 창 25개 + 데이트 | 4.3 / 4.8 (같은 시각 API 가 전반적으로 느렸다 — 분절은 1.0초, 나머지가 데이트 체인) |

이 벤치는 다른 실험과 동시에 돌아 API 응답이 전반적으로 0.3~0.5초 느렸다. 줄어든 폭은
위 표와 같다 — 분절이 창 크기와 무관하게 1초 아래로 고정된다는 것이 핵심이다.

## 7. 방이 여러 개가 되면서 확인한 것 — 이번에 고치지 않은 것

레이턴시와 무관하지만 코드를 훑다 확인한 것이라 적어 둔다. **판단이 필요해서 손대지
않았다.**

1. **기억 저장소가 방 단위가 아니다.** `data/memories.json` 은 전역 하나고 `Memory` 에
   방 id 가 없다. 방 X 에서 추출한 "마라탕 땡긴다"가 방 Y 의 데이트 코스 근거로 인용될
   수 있다 — "지난주에 마라탕 땡긴다고 하셨던 거"가 **다른 커플의 말**이 된다. 시드 27건은
   시연 방(1번)을 위한 것인데 새 방에도 똑같이 보인다. 고치려면 `Memory.room` 을 붙이고
   추출·검색을 방으로 가르되 **시드를 어느 방에 줄지**(전부? 1번만?)를 정해야 한다.
   → **사용자 결정으로 일단 파킹했다 (8장).**
2. **말투 기준선 시드도 전역이다.** `data/speaker_profiles.json` 의 A·B 는 시연 커플의
   기준선인데 모든 방의 A·B 에 적용된다. 서버가 `speakerProfiles` 를 실어주면(합의됐으나
   미전송, `server-handoff.md` 10장 2번) 해결된다 — 요청 값이 시드보다 우선한다.
   → **사용자 결정으로 공통 기준선 하나로 바꿨다 (9장).**
3. **동시 요청.** 방이 늘면 요청이 겹친다. 워커는 요청마다 스레드풀이라 서로 안 밀리고
   (동시 3건 실측 8.0초, 개별과 같음), 백그라운드 추출 풀은 4개다. 병목은 OpenAI 쪽
   분당 요청 한도다 — 요청 하나가 LLM 을 4~6회 부르니 방 10개가 5초마다 한 마디씩 하면
   분당 500~700회다. 한도에 걸리면 LangChain 이 조용히 재시도해서 "느린 호출"로만 보인다
   (`SLOW_CALL_SECONDS` 경고가 그 신호). 조직 한도(RPM/TPM)를 한 번 확인해 둘 것.
4. **점수 캐시는 방 id 로 나뉜다.** 서버가 `chatRoomId` 를 재사용해도 내용 지문이 달라
   섞이지 않는다.

## 9. 말투 기준선을 공통값 하나로 (같은 날, 사용자 결정)

7장 2번. 선택지는 셋이었다 — 서버가 방별로 집계해 실어줌 / 워커가 방별로 메모리에 누적 /
**평균적인 사람의 말투 하나**. 하루 시연이라 셋째로 정했다. 시연 커플 시드는
`parked/speaker_profiles.json` 으로 옮기고, `profile.GENERIC_PROFILE` 이 모든 방·화자의
기준선이 된다. 요청에 `speakerProfiles` 가 오면 여전히 그쪽이 우선한다.

| | 값 | 근거 |
| --- | --- | --- |
| `avg_length` | 14 | 픽스처 156발화 평균 12자, 시연 시드 18~21자 사이 |
| `period_rate` | 0.05 | 픽스처 2%, 시드 3~5%. 임계 0.15 아래라 "됐어." 류 마침표 종결은 신호로 센다 |
| `laugh_per_msg` | 2.0 | 시드 2.0~2.8 (카톡에서 ㅋ 은 흔하다). 임계 1.5 이상이라 ㅋ 이 사라진 진지한 메시지는 신호 하나 |
| `emoji_rate` | 0.15 | 임계 0.3 아래 — 안 쓰는 사람이 많아 부재를 세지 않는다 |
| `top_address` | 없음 | 특정 애칭을 가정하지 않는다. 거친 호칭은 전부 "평소와 다름" |

외부 평가셋(MSD 2000건)에서 뽑으려 했으나 존댓말·마침표 종결의 격식 대화라(마침표 종결
~90%, ㅋ 0) 카톡의 평균으로 쓸 수 없었다.

**들어온 대화에서 계산하는 폴백도 뺐다** — 창 30개로 "평소"를 잡으면 방금 화난 메시지가
섞여 변화량이 안 잡힌다는 것이 원래의 설계 이유였다.

회귀 (CLI, 공통 기준선 적용 후):
