## 1. 문제 — 픽스처가 가리고 있던 것

규격서 3장의 흐름은 이렇다.

```
백엔드의 메시지 저장 → 설정된 메시지 개수 누적 → AI 워커에 공통 분석 요청
```

**서버는 최근 N개를 통째로 보낸다. 화제 경계를 모른다.** 그런데 워커의 게이트는 전부
고정 창(최근 12개)이었다. "최근 12개"는 **개수**지 **대화**가 아니다.

### 실측 — 실제로 깨졌다

```
[20:02] A  이번 주 토요일에 뭐 하지? 우리 성수 갈까     ← 주말 약속
[20:04] B  좋지 카페 가고 싶다 ㅎㅎ
[20:06] A  배고파 마라탕도 땡기는데
[20:10] B  이따 얘기하자 나 지금 좀 바빠
        ⋯ 2시간 20분 침묵 ⋯
[22:30] A  연락 왜 안 봐                              ← 연락 문제로 다툼
[22:37] A  너 맨날 이런 식이지.
```

```
TONE_CORRECTION      INDIVIDUAL → USER_A   trigger=[208]        ← 맞다
DATE_RECOMMENDATION  COUPLE                trigger=[201, 202]   ← 나가면 안 된다
```

**막 싸우기 시작한 사람들에게 데이트 코스가 나갔다.** 그리고 **LLM 게이트도 못 막았다**
(`should_recommend=true`) — 창 안에 있으면 LLM 에게도 "지금 대화"로 보인다. 판정을 아무리
잘해도 재료가 섞이면 소용이 없다. `fixtures/case11_mixed.json` 이 이 케이스다.

## 2. 세그먼트란 무엇인가

> **세그먼트** — 같은 화제로 이어지는 연속 메시지 묶음. **라우팅과 기억 추출의 단위.**

라우팅은 **활성 세그먼트(= 마지막 세그먼트)에만** 건다. 개입은 지금 벌어지고 있는 대화에
대해서 하는 것이다. 두 시간 전에 끝난 화제에 지금 카드를 띄우는 건 늦은 게 아니라 틀린 것이다.

## 3. 판정 구조 — 점수는 LLM, 자르는 건 룰

### 3-1. 왜 바꾸는가

처음 구현은 **LLM 에게 대화를 통째로 주고 세그먼트 목록을 받는** 배치 방식이었다.
동작은 했지만 세 가지가 걸린다.

| | 배치 방식(전환 전) | 점수 방식(현재) |
| --- | --- | --- |
| 경계 결정 | LLM 안에서. **읽을 수도 고칠 수도 없다** | 코드의 임계값. 읽히고 튜닝된다 |
| 왜 잘렸나 | 알 수 없다 | 발화별 점수가 트레이스에 남는다 |
| 출력 검증 | id 분할이 정확한지 전량 대조. 어긋나면 통째로 폴백 | id 로 맞춰 붙인다. 하나 빠져도 그 발화만 넘어간다 |

**경계가 코드 밖에 있으면 조정할 손잡이가 없다.** 과분절이 나와도 프롬프트를 다시 쓰는 것
말고 할 수 있는 게 없고, 그건 재현 가능한 조정이 아니다.

### 3-2. 구조

```
messages
   ↓
① 룰 컷      3시간 이상 공백에서 자른다 (LLM 에게 묻지 않는다)
   ↓
② LLM 채점   마지막 조각의 발화마다 "직전 맥락과 얼마나 이어지는가"를 점수로 (호출 1회)
   ↓
③ 룰 판정    임계값으로 붙일지 자를지 결정한다
   ↓
segments[]   [ … 과거 … , 활성 ]
```

**LLM 은 경계를 정하지 않는다. 점수만 낸다.** 자르는 판단은 전부 ③에 있다.

### 3-3. LLM 이 내는 값

발화 하나하나에 대해 **직전까지의 맥락과 비교**해서 매긴다.

| 필드 | 범위 | 뜻 |
| --- | --- | --- |
| `same_context` | true/false | 이전 맥락과 같은 이야기인가 |
| `topic_score` | 0~100 | **화제가 이어지는 정도.** 100 에 가까울수록 같은 얘기 |
| `tone_score` | 0~100 | **말투가 이어지는 정도.** 100 에 가까울수록 평소 흐름 |

> ⚠️ **이름 주의.** "변화 점수"가 아니라 **연속성 점수**다. 높을수록 **안 바뀐 것**이다.
> 90~80점대면 "이전 맥락과 비슷하다"가 되도록 방향을 맞춰 놨다.

**점수 앵커를 프롬프트에 명시한다.** LLM 이 매기는 숫자는 그냥 두면 보정이 안 된다 —
85 와 75 의 차이가 호출마다 달라진다. 기준점을 글로 박아야 임계값이 의미를 갖는다.

```
100  같은 것에 대해 계속 말하고 있다
 80  이어지는 이야기다 (앞의 내용이 원인이거나 부연이다)
 50  느슨하게 연결된다 (앞의 이야기에서 흘러왔지만 초점이 옮겨갔다)
 20  다른 이야기다 (앞의 내용과 상관없이 새로 꺼냈다)
  0  완전히 무관하다
```

### 3-4. 룰이 판정한다

```python
CUT_HARD   = 35   # 이 아래면 무조건 자른다
KEEP_SOFT  = 90   # 이 위면 무조건 붙인다
TONE_CUT   = 40   # 회색지대에서만 쓰는 보조 기준
GAP_SOFT   = 30분  # 회색지대에서만 쓰는 보조 기준
```

> **이 값은 앵커에서 역산했다.** 처음에 `CUT_HARD=50` · `KEEP_SOFT=80` 으로 뒀더니
> `case11` 이 통째로 안 잘렸다. 모델이 **거의 앵커 값만 쓰기 때문**이다 — 실측에서
> 100·80·50 만 나왔다. 진짜 경계(2시간 20분 뒤 다툼 시작)가 80 을 받았는데 `KEEP_SOFT=80`
> 이면 무조건 유지로 빠진다.
>
> 앵커를 다시 보면 **"80 = 이어지는 이야기"는 유지 근거가 아니다.** 이어진다는 것과 같은
> 대화라는 것은 다르다. 무조건 유지할 것은 `100`(같은 것) 뿐이고, 무조건 자를 것은
> `20`(다른 이야기) 이하뿐이다. 그래서 임계값은 **앵커 사이에** 놓는다.
>
>     100 ──┐ KEEP_SOFT=90        무조건 유지
>      80   │ 회색지대            시간 공백·말투가 결정
>      50   │
>      20 ──┘ CUT_HARD=35         무조건 자름

```
topic_score >= KEEP_SOFT              → 붙인다
topic_score <  CUT_HARD               → 자른다
그 사이(회색지대)                       → 보조 신호로 결정한다
    시간 공백 >= GAP_SOFT  이거나
    tone_score < TONE_CUT 이면서 same_context == false  → 자른다
    아니면 붙인다
```

**회색지대에서는 붙이는 쪽이 기본값이다.** 잘못 자르면 뒤 단계가 맥락을 잃지만, 안 자르면
분절 전과 같아질 뿐이다. 되돌릴 수 있는 실수를 택한다.

### 3-5. 말투 점수는 단독으로 자르지 않는다

`tone_score` 는 받되 **회색지대의 보조 신호로만** 쓴다. 말투만으로는 절대 자르지 않는다.
근거는 `case7_tone` 이다.

```
101 A  오빠 오늘 몇 시에 와? 저녁 같이 먹으려고 기다리고 있었어
102 B  아 미안 오늘 야근 잡혀서 못 갈 것 같아          ← 화가 난 원인
103 A  또? 지난주에도 그랬잖아
105 A  야 너는 맨날 그런 식이야.
```

호칭이 `오빠` → `야` 로 바뀌고 이모지·ㅋ 가 사라지고 마침표로 끝난다. **말투는 극적으로
바뀌는데 화제는 처음부터 끝까지 저녁 약속 하나다.**

여기서 자르면 활성 세그먼트가 `[105]` 만 남고, 말투 판정에서 **102 가 통째로 빠진다.**
그러면 지금 나오는 대체 문장

> "오늘 못 온다니까 좀 서운했어, 다음엔 미리 말해줘"

가 나올 수 없다. 왜 화가 났는지를 모르니까. 남는 건 "감정이 올라와 있는 것 같아요" 수준의
일반론이고 그건 대체 문장이 아니다. **말투 교정이 자기 발밑을 파는 구조가 된다.**

말투 정보는 자르는 대신 `tone_score` 로 트레이스에 남는다. **말투는 "어디서 자를까"가
아니라 "무엇을 내보낼까"에 쓰는 신호다** (`SUPPRESS_YOUTUBE_WHEN_TONE` 이 이미 그 자리에 있다).

실측에서 이게 그대로 보인다 — `case7` 은 말투 점수가 103 에서 80, 105 에서 90 으로 떨어지는데
화제가 계속 100 이라 안 잘린다.

### 3-6. 비교 기준은 "지금 흐르고 있는 화제"다 — 실측으로 고친 것

전환 직후 실사용에서 **과분절**이 나왔다. 다툼이 계속되는데 발화마다 잘렸다.

```
A: 나는 후룸라이드 타고 싶당
B: 너 다른 남자랑 가봤어?                     화제 20  → 자름 (맞다)
A: 그게 무슨소리야 니가 다른 여자랑 가봤겠지   화제 20  → 또 자름 (틀렸다)
B: 또 그딴소리하네                            화제 20  → 또 자름 (틀렸다)

세그먼트 4개   114~117 | 118~120 | 121~121 | 122~122
```

`그게 무슨소리야…` 는 바로 앞 의심에 대한 **직접 반박**인데 20 을 받았다. 모델이 직전
흐름이 아니라 **원래 화제(놀이공원)와 비교**하고 있었다. 화제가 한 번 바뀐 뒤로는 계속
"원래 얘기가 아니다" 판정이 나온다.

**그리고 이게 경계 흔들림으로도 나타났다.** 발화를 하나 더 넣으면 전체가 재채점되는데,
다툼이 더 길게 보이니 모델이 앞 발화를 다시 100 으로 매겨서 **잘려 있던 게 갑자기 붙었다.**

```
9개일 때 :  121~121 | 122~122     따로
10개일 때:  121~123               합쳐짐
```

사용자가 본 증상은 "합쳐짐"이지만 원인은 과분절 쪽이었다.

프롬프트에 세 가지를 못박아 고쳤다.

- **대화가 처음에 무엇으로 시작했는지는 상관없다.** 화제가 바뀌었으면 바뀐 화제가 새 기준이다
- **응답·반박·되물음은 이어지는 것이다.** 내용이 날카로워도 같은 실랑이면 100 에 가깝다
- **낮은 점수를 연달아 주고 있다면 대개 틀린 것이다** — 기준을 원래 화제에 두고 있는지 확인한다

고친 뒤 3회 연속 동일한 결과가 나오고, 발화를 추가해도 경계가 그대로다.

```
9개 :  114~117 | 118~120 | 121~122      118:20  121:20  나머지 전부 100
10개:  114~117 | 118~120 | 121~123      경계 그대로, 마지막만 붙는다
```

> 낮은 점수가 **화제가 바뀌는 지점에만 하나씩** 찍히는 게 정상이다. 연달아 찍히면 프롬프트를
> 의심한다.

### 3-7. 호출은 요청당 1회로 유지한다

발화마다 LLM 을 부르면 메시지 20개짜리 요청이 20회가 된다. 그래서 **한 번의 호출로 발화별
점수 배열을 받는다.**

```
입력   [1] (20:02) A: 이번 주 토요일에 뭐 하지? 우리 성수 갈까
       [2] (20:04) B: 좋지 카페 가고 싶다 ㅎㅎ
       ...
       [6] (22:30) A: 연락 왜 안 봐

출력   scores: [
         {message_id: 202, same_context: true,  topic_score: 100, tone_score: 100, note: "..."},
         ...
         {message_id: 206, same_context: true,  topic_score: 50,  tone_score: 50,  note: "..."}
       ]
```

첫 발화는 비교 대상이 없으므로 채점하지 않는다.

**점수가 빠지거나 엉뚱한 id 가 섞여도 통째로 버리지 않는다.** 아는 id 만 남기고, 점수가 없는
발화는 "안 자름"으로 넘어간다. 처음에는 전량 대조로 하나라도 어긋나면 조각 전체를 세그먼트
1개로 되돌렸는데, **대화가 길수록 어긋날 확률은 올라가는데 잃는 것도 같이 커지는** 최악의
조합이었다 — 길게 나눠 놓은 경계가 통째로 사라진다.

호출 자체가 실패했을 때만 조각 전체를 1개로 되돌린다 (= 분절 전 동작).
점수를 순서대로 `zip` 하지 않고 **id 로 찾는다.** 하나 빠지면 뒤가 전부 한 칸씩 밀려서
엉뚱한 자리에서 잘리기 때문이다.

배치 방식과 호출 수는 같고, 달라지는 건 **경계 결정이 코드로 나온다는 것**이다.

### 3-8. 시각을 프롬프트에 넣는다

전환 전에는 `[id] sender: content` 만 넣어서 **LLM 이 시간 공백을 아예 못 봤다.** 2시간
50분이 벌어져도 안 보였다 — 3시간 룰 컷 바로 아래 구간이 통째로 사각지대였다.

지금은 `[id] (MM-DD HH:MM) sender: content` 로 넣는다. 다른 프롬프트에서
`text.format_transcript()` 가 하는 일과 같다(데이트 코스가 "밤 10시에 브런치"를 안 넣는
근거가 이것이다).

**회색지대 판정에서 시간 공백이 실제로 결정타 역할을 한다.** `case11` 의 경계 발화는
실행마다 80 또는 50 을 받아 늘 회색으로 떨어지는데, 140분 공백이 매번 같은 결론을 낸다.

## 4. 룰 컷 — 시간 공백

```
GAP_HARD = 3시간   이 이상 벌어지면 LLM 에게 묻지 않고 자른다
```

**실측으로 정한 값이 아니다.** 단일 화제 안 최대 공백이 9분이고 경계가 140분 이상이라 그
사이에 표본이 없다. 룰 컷은 *LLM 없이 확정*이라 **잘못 자르면 고칠 기회조차 없어서**,
넉넉하게 잡고 애매한 것은 전부 채점으로 넘긴다.

**이 컷이 필요한 이유는 실측으로 확인됐다.** LLM 은 화제는 보는데 시간을 못 본다 —
`case4_routine`(사흘치, 공백 1432분·1445분)을 3회 모두 "일상 대화" 한 덩어리로 봤다.
화제가 같으니 LLM 입장에선 틀린 판단이 아니다. 룰 컷이 정확히 이 구멍을 메운다.

> 숫자와 LLM 중 하나를 고르는 문제가 아니라 **서로 다른 구멍을 메우고 있다.**

## 5. 경계 신호로 재보고 버린 것들

시간 공백 말고 룰로 쓸 신호가 있는지 네 가지를 실측했다. **셋이 무너졌다.**

| 방식 | 결과 |
| --- | --- |
| 화제 전환 표지어 | ❌ **반대로 작동** |
| 어휘 겹침 | ❌ **변별력 0** |
| 임베딩 거리 | ❌ **경계에서 오히려 낮음** |
| 시간 공백 | ✅ 유일하게 갈림 |

**표지어** — `case9_date` 는 단일 화제인데 세 번째 메시지가 `근데 만나서 뭐하지?` 로
시작한다. 반대로 실측 스트림의 진짜 경계(`206 연락 왜 안 봐`)에는 표지어가 없다.
사람은 "그건 그렇고"라고 선언하고 화제를 바꾸지 않는다. 그냥 바꾼다.

**어휘 겹침** — 직전 3개와의 2글자 이상 토큰 교집합.

| | 겹치는 단어 수 |
| --- | --- |
| `case9` 같은 화제 안 인접 발화 | 0, 0, 0, 0, 1 |
| 실측 스트림의 진짜 경계 | 0 |

조사가 붙어 `토요일에` 와 `토요일` 이 다른 토큰이고 채팅 문장이 짧다. **같은 화제에서도
0 이면 신호가 아니다.** 게다가 `case4_routine` 은 사흘 내내 같은 인사를 한다 —
**어휘는 거의 같은데 다른 대화 3개다.** 못 잡는 정도가 아니라 반대로 잡는다.

**임베딩 거리** — `retrieve.py` 가 이미 쓰는 `OpenAIEmbeddings` 로 인접 블록 코사인 거리.

```
실측 스트림 (진짜 경계는 206 하나)
  202  0.764   ← 같은 화제인데 최대
  206  0.521   ← 진짜 경계인데 최소 축
```

`case9`(단일 화제) 범위가 0.536~0.689, 경계 있는 스트림이 0.506~0.764로 **분포가 통째로
겹친다.** 짧은 채팅에서 임베딩은 화제보다 **발화 형식**(질문·사과·리액션)을 더 반영한다.

> **결론** — 화제 전환은 문자열이나 벡터 표면에 흔적을 거의 안 남긴다. 표면 특징으로 풀 수
> 있는 문제가 아니라서 **의미 판정(LLM 채점)** 이 필요하다. 룰의 몫은 시간과 임계값이다.

## 6. 어느 세그먼트를 분석하는가

라우팅은 **활성 세그먼트에만** 건다. 1장의 고장은 이 규칙 하나로 고쳐진다 — 데이트
발화(201~205)는 활성이 아니므로 게이트가 아예 그 메시지를 보지 않고, `triggerMessageIds`
도 자동으로 활성 세그먼트 안에 갇힌다.

**맥락과 트리거를 갈라 쓴다.** 이게 6장의 핵심이다.

| | 쓰는 것 | 이유 |
| --- | --- | --- |
| 게이트 · 트리거 id · RAG 질의 · 기억 추출 | **활성 세그먼트만** | 과거 화제가 기능을 발동시키면 안 된다 |
| 말투 판정 프롬프트의 직전 대화 | **맥락(활성 + 부족분)** | 활성이 1개면 장난인지 갈등인지 구분할 수 없다 |
| 말투 기준선(`profile.py`) | **전체 스트림** | 기준선은 표본이 넓을수록 정확하다 |

| 상황 | 처리 |
| --- | --- |
| 활성 세그먼트가 4개 미만 | 앞 세그먼트에서 뒤에서부터 채워 맥락 4개를 확보한다 |
| 세그먼트가 1개다 | 분절 전과 완전히 같다 |

**규격서 6장의 "여러 기능 동시 발동"을 어기지 않는다.** 제한하는 것은 *기능 개수*가 아니라
*화제*다.

## 7. 화제 라벨을 만들지 않는다

배치 방식일 때는 세그먼트마다 `topic`(`"주말 계획"`) · `mood` 라벨이 붙었다.
**점수 방식에서는 만들지 않는다.**

만들 수가 없다 — 경계를 룰이 **나중에** 정하므로, 채점 시점의 LLM 은 세그먼트가 어디서
어디까지인지 모른다. 억지로 받아내려면 발화마다 라벨을 달게 해야 하는데 그럴 이유가 없다.

**안 만드는 게 오히려 안전하다.**

> ⚠️ LLM 이 라벨에 `"권태기 조짐"`, `"요즘 대화가 줄어든 것에 대한 다툼"` 같은 문자열을
> 붙일 수 있다. 이 프로젝트의 **절대 제약** 정면 위반이다. `filter.py` 는 `AiResult` 의
> 화면 문자열만 검사하므로 라벨은 걸러지지 않는다. 라벨 자체가 없으면 이 위험이 사라진다.

디버깅 정보는 점수와 `note` 가 대신하고, 그쪽이 더 정밀하다 — "왜 이 세그먼트인가"가
아니라 **"왜 여기서 잘렸는가"**를 알려주기 때문이다. `note` 에도 관계 상태를 쓰지 못하게
프롬프트로 막아뒀고, 트레이스 밖으로 나가지 않는다.

**`tone_score` 를 규격서 11장의 감정 분석(`emotionAnalyses`)과 섞지 않는다.** 그쪽은 명세가
없는 별도 기능이고 화면에 나간다. `tone_score` 는 절대값이 아니라 **직전 대비 연속성**이라
애초에 다른 값이다.

## 9. 비용과 레이턴시

`devui` 가 단계별로 계측한다 (`worker/llm.py` 의 `USAGE.records` — 호출마다 출력 스키마
이름·시간·토큰을 남긴다).

| 케이스 | 총 소요 | LLM | 외부 API·룰 | 그중 분절 호출 |
| --- | --- | --- | --- | --- |
| `case11_mixed` (8개, 결과 1건) | 7.0초 | 4회 5.9초 | 1.1초 | 2.0초 |
| `case9_date` (6개, 카카오 3회) | 8.3~8.7초 | 4회 6.6~7.4초 | 1.2~1.7초 | 1.5~1.7초 |

### 근거 문구(`note`)를 받지 않는다 — 분절 호출 절반

처음에는 발화마다 `note` 를 한 줄씩 받았다. 8개짜리 대화면 근거 문장을 7개 생성하느라
출력이 292 토큰이 되고 **분절 호출이 4.0초**였다.

빼고 두 케이스를 5회씩 끝단으로 돌렸다.

| | 분절 호출 | 경계 정확도 |
| --- | --- | --- |
| `note` 있음 | 4.02초 / 3.84초 | 5/5 |
| **`note` 없음** | **2.31초 / 2.64초** | **5/5** |

**경계가 완전히 같다.** 잃는 것은 "왜 그 점수인지"뿐이고, **"왜 잘렸는지"는 점수·임계값·
공백으로 이미 계산되어 화면에 나온다** — `note` 는 2차 정보였다.

> ⚠️ **"점수가 높을 때만 `note` 를 생략" 하는 절충은 하면 안 된다.** 실측에서 모델이 쉬운
> 길로 쏠려 **점수를 전부 100 으로 매기고 경계를 통째로 놓쳤다.** 조건부로 일을 줄여주면
> 그 조건 쪽으로 답이 쏠린다. 지우려면 완전히 지운다.

### 외부 API 를 동시에 부른다

카카오 검색은 서로 독립인데 검색어마다 순차로 돌고 있었다. **실측 0.75초 → 0.20초.**
유튜브의 `commentThreads`(후보마다 1회)도 같은 이유로 동시에 부른다.

지역명이 없을 때만 순차가 남는다 — **첫 장소가 코스의 중심**이라 그것만 먼저 확정해야
한다(`build_course`). 첫 검색이 비어서 중심을 못 잡으면 원래대로 순차로 돈다.

`case9` 의 외부 API·룰 구간이 3.2초 → 1.2~1.7초로 줄었다 (RAG 임베딩 호출 포함).

병렬화가 안 되는 곳: **모든 후보가 분절 결과를 기다린다.** 후보 기능끼리의 병렬 실행은
`SUPPRESS_YOUTUBE_WHEN_TONE` 때문에 유튜브가 말투 결과에 의존해서, 말투·데이트만 묶을 수
있다. 타임아웃 기준이 정해진 뒤에 한다 (`worker-tasks` 14단계).

### 그래도 순증이 아니다

1장 실측 기준으로 데이트 코스가 미발동하면서 LLM 2회와 카카오 2회가 통째로 빠진다 —
**1회를 더하고 3회를 빼서 순감이다.**

```
분절 전   extract + tone_judge + tone_suggest + plan_date + write_reason  = 5회 + 카카오 2회
분절 후   segment + extract + tone_judge + tone_suggest                   = 4회 + 카카오 0회
```

### 생산 창 30개에서 분절이 직렬 병목이 된다 — 분할 동시 채점 (2026-08-19)

위 표는 픽스처(6~10개) 기준이다. **서버는 최근 30개를 보낸다** — 그리고 분절 출력이
발화당 ~20토큰(id·점수 2개·bool)이라 **창 크기에 선형으로 비례한다.** 배포 단건 반영이
10.4~14.4초였는데, 백엔드 지연을 걷어내고 보니 전부 이 구간이었다.

합성 창(잡담, 발화 간 2분)으로 스케일을 재면:

| 창 크기 | 분절 호출 | 출력 토큰 |
| --- | --- | --- |
| 10개 | 4.5초 | 185 |
| 20개 | 5.3초 | 385 |
| **30개 (생산)** | **7.4초** | 585 |
| 40개 | 9.9초 | 785 |

시도한 것 셋. 검증은 전부 **픽스처 18종 경계 동일 + K=30 합성 경계 동일**이 기준이다.

1. **필드명 축약** (`message_id`·`same_context`·`topic_score`·`tone_score` →
   `id`·`same`·`topic`·`tone`) — 필드명이 발화마다 반복되므로 출력 −19%. 경계 18종
   동일. **시간은 거의 안 줄었다** (K=30 6.7~8.1초) — 토큰보다 모델 출력 속도가 병목.
   정보 손실이 없어서 그대로 두되, 이것만으로는 답이 아니다.
2. **분절만 `gpt-4.1-nano`** — 새 스키마로 재확인했고 **또 탈락.** case2 4→1,
   case5 2→1 로 경계를 통째로 잃고 case11 이 2→3 으로 흔들린다. 17장(worker-tasks)의
   "nano 전 단계 탈락" 결론이 스키마를 바꿔도 유지된다.
3. ✅ **분할 동시 채점** (`SCORE_BATCH = 15`) — 채점 대상이 15개를 넘으면 배치로 나눠
   **동시에** 부른다. 각 배치는 자기 앞의 전체 발화를 "앞 맥락 (채점하지 않는다)"
   구획으로 그대로 보므로 **판단 재료는 한 호출일 때와 같고 출력만 나뉜다.**

   | | 분절 호출 (K=30) | 경계 |
   | --- | --- | --- |
   | 단일 호출 | 7.4초 | [8,4,2,4,4,4,4] |
   | **분할 2배치** | **3.9초** | **동일** |

   실패 반경도 그대로다 — 배치 하나가 실패하면 그 구간만 "안 자름"이 되고(빠진 점수의
   기존 처리와 같음) 나머지 경계는 산다. 채점 대상 15개 이하(픽스처 전부)는 기존 단일
   호출 경로 그대로라 형식 변화가 없다.

**배포 실측 (2026-08-19 저녁, main 병합 후).** 단건 반영 10.4~14.4초 → **6.1~8.2초**
(5회), 10건 버스트 최종 반영 +11.2초(분석 3건으로 접힘 — 서버 코얼레싱 유지).

같은 워커 코드가 아침엔 10초, 낮엔 14초까지 오간 이유도 이 선형성으로 설명된다 —
**룰 컷(3시간)이 어디서 잘리느냐에 따라 채점 대상이 몇 개냐가 달라진다.** 방이 밤새
조용했으면 마지막 조각이 작아서 빠르고, 대화가 3시간 안에 이어지면 조각이 창 전체(30개)
로 자라 느려진다. 분할 채점은 이 변동폭 자체를 눌러 놓는다.

---

### 같은 발화를 요청마다 다시 채점하지 않는다 — 점수 캐시 (2026-09-13)

분할 채점으로 창 30개가 3.9초가 됐지만, **매 요청 30개를 전부 다시 채점하고 있었다.**
백엔드는 메시지 1건마다 창을 통째로 보내므로 요청 N+1 에서 새로 온 발화는 한두 개다.
발화 하나의 점수는 "직전까지의 맥락과 얼마나 이어지는가"라 **같은 발화·같은 직전 발화면
재료가 같다.** 그래서 (방, 발화 id) 로 점수를 기억하고, 캐시에 없는 꼬리만 그 앞 전체를
'앞 맥락' 구획으로 붙여 채점한다 — 분할 채점의 배치 하나와 형식이 같다.

| | 분절 호출 (창 25개, 슬라이딩) | 출력 토큰 |
| --- | --- | --- |
| 캐시 없음 (2배치) | 1.8~1.9초 | 209 + 209 |
| **캐시 적중 21/24** (꼬리 3개 재채점) | **0.55~0.9초** | ~33 |

**경계 검증.** 픽스처를 메시지 하나씩 늘려가는 요청 열(백엔드와 같은 조건)로 돌려 마지막
창의 경계를 콜드 전량 채점과 비교했다 — case11 [5,3]·case19 [10,4]·case1·case3·case4 동일.
**case2(2개짜리 소화제 4개)는 새 발화 하나만 채점하면 3/4 에서 경계를 잃었다** — 채점
대상이 짧을 때 관대해지는 같은 현상이라, 캐시가 있어도 꼬리 `SCORE_TAIL_MIN` 개는 매번
다시 채점한다. 자세한 표는 `docs/refactoring.md`.

**부수 효과가 좋은 쪽이다.** 같은 발화의 점수가 요청마다 안 흔들려서 세그먼트 경계가
안정된다 — 유튜브·데이트의 "같은 화제엔 하나만" 억제가 세그먼트 시작 시각에 기대고
있어서, 경계가 흔들리면 억제가 새던 자리다.

**무상태 원칙과의 관계.** 상태가 아니라 메모다 — 비어 있으면(재시작·다른 인스턴스) 전부
다시 채점하고 결과 규칙은 안 바뀐다. 키에 직전·이번 발화의 내용 지문을 넣어 픽스처처럼
방 id 와 발화 id 가 겹치는 경우를 막는다. `KAKAPO_SEGMENT_CACHE=0` 으로 끈다.

> ⚠️ **`SCORE_BATCH` 를 10 으로 줄여봤다가 되돌렸다.** 캐시 끄고 3회씩 재보니 배치가
> 작으면 경계를 잃는다 — case19 [10,4] → [14] 3/3, case21 의 4·4 가 8 로 합쳐짐 3/3.
> 채점 대상이 짧으면 모델이 낮은 점수를 안 준다. 15 는 그 경계가 유지되는 값이다.

## 12. 검증

### 12-1. 점수 보정부터 잰다 (1순위)

임계값을 정하려면 점수가 안정적인지부터 알아야 한다. **같은 대화를 5회씩 채점해 발화별
점수의 분산을 본다.** 분산이 크면 임계값 방식 자체가 성립하지 않으므로, 그때는 점수를
버리고 이산 등급(`same` / `related` / `shifted` / `unrelated`)으로 내린다.

### 12-2. 임계값을 점수 분포에서 정한다

경계인 곳과 아닌 곳의 점수 분포를 그려서 겹치는 구간을 회색지대로 잡는다.
데이터는 `data/eval/msd_sample.jsonl`(실제 한국어 대화 2000건)을 쓴다.

- **과분절률** — 단일 세션(한 대화)이 세그먼트 1개로 나오는가
- **경계 탐지** — 다른 주제 대화 둘을 **30분 간격**으로 이어붙인다. 3시간 컷 미만이라
  룰이 안 걸리고 채점만으로 찾는지 격리해서 볼 수 있다

> ⚠️ **시간 공백 임계값은 이 데이터로 검증되지 않는다.** 빌더가 세션 내 `sentAt` 을 1~5분
> 랜덤으로 **생성**한다(원본에 시각이 없다). `gapDays` 만 원문에서 읽은 진짜 값인데 일
> 단위라 3시간 컷은 무조건 걸린다. 임계값은 실서비스 로그가 쌓여야 정할 수 있다.

### 12-3. 픽스처 회귀

| `case11_mixed` | 세그먼트 2개(`201~205` / `206~208`), **데이트 코스 미발동**, 말투 교정만 |

## 2. 화면 구조 — 위젯은 딱 2줄이다

**PM 확인 (2026-08-17).** 상단 위젯에 뜨는 것은 **두 줄, 그게 전부다.**

```
┌───────────────────────────────────┐
│  ① 서운해 보여요                    │  ← 감정 상태. 상시. 비지 않는다
│  ② 카카포가 추천하는 장소를 …        │  ← 3종. 미발동이면 null (빈 줄)
├───────────────────────────────────┤
│  A: 오늘 뭐했어?                    │
│  B: 그냥 집에 있었어                 │  ← 커플만의 공간
└───────────────────────────────────┘
```

| | 줄 | 내용 | 미발동 시 |
| --- | --- | --- | --- |
| ① | 감정 상태 | 이 문서의 기능. 10자 이하 | **없음 — 항상 찬다** |
| ② | 개입 | 데이트 코스 / 유튜브 / 말투 교정 | **`null` — 빈 줄** |

**이 구조가 이 문서의 설계 대부분을 결정한다.**

- **두 줄은 자리를 다투지 않는다.** 3종이 전부 미발동이어도 ②만 비고 ①은 그대로다 →
  5장의 배열 분리(`emotionAnalyses` / `results`)가 화면과 1:1로 맞는다
- **"비어 있음"의 의미가 줄마다 다르다.** ②의 빈 줄은 정상 상태(`SKIPPED` 의 화면)고,
  ①의 빈 줄은 **있으면 안 되는 상태**다
- **①은 글자다.** 워커가 내보내는 10자가 그대로 화면 한 줄이 된다. 그래서 문구의 안전을
  워커가 끝까지 책임져야 한다 (3장·6장)

> **"사랑끈"은 ①번 줄의 시각 컨셉이다.** 별도의 그림 영역이 아니라 이 한 줄을 어떻게
> 보여줄지의 문제다. **디자인 확정 (2026-08-17)** — 상태 라벨 5종마다 실 모양과 글로우가
> 정해졌다 (6장 표). 워커는 라벨과 강도(`emotionType`·`intensityValue`)를 실어 보내고,
> 그걸로 무엇을 그릴지는 그 표가 정한다 (3-2).

### 기존 3종과 다른 점

기존 3종을 만들 때 세운 전제가 여기서는 전부 뒤집힌다. 같은 틀에 넣으면 안 된다.

| | 기존 3종 | 실 상태 표현 |
| --- | --- | --- |
| 발동 | 게이트 통과 시에만 | **상시** |
| 기본값 | **침묵** — 애매하면 개입하지 않는다 | 항상 무언가 뜬다 |
| 화면 자리 | **②번 줄** (셋이 한 자리를 나눠 쓴다) | **①번 줄** (독점) |
| 노출 단위 | 결과 1건을 누구에게 보일지 | **보는 사람마다 내용이 다르다** |
| 출력 길이 | 문장 | **10자** |
| LLM 비용 | 게이트가 걸린 요청만 | **매 요청 고정 비용** |

> ### 워커 노트 — "침묵이 기본값"이 여기서는 성립하지 않는다
>
> 지금까지 이 워커의 안전장치는 전부 **안 내보내는 것**이었다. 유튜브는 후보 전원이
> 부적합하면 침묵하고, 데이트 코스는 카카오 결과가 부족하면 미발동하고, 말투 교정은
> 금지어에 걸리면 재생성 1회 후 버린다. **이 기능에는 그 손잡이가 없다.**
> 명세가 "null 처리 예외 — 항상 출력"으로 못박았기 때문이다.
>
> 그래서 안전은 **출력 단계가 아니라 설계 단계에서 미리 확보해야 한다.**
> 6장(문구를 사전에서 고른다)과 7장(중립을 기본 라벨로 둔다)이 그 대응이다.

## 3. 절대 제약과의 충돌 — 가장 먼저 정리해야 할 것

`CLAUDE.md` 의 절대 제약은 이 프로젝트의 핵심 가치다.

> **관계 상태를 언급하는 문구를 절대 출력하지 않는다.**
> 내가 눈치채기 전에 kakapo가 먼저 눈치채고 조용히 회복시킨다.

그런데 이 명세의 첫 문장은 **"감정 상태, 관계를 진단하고"** 다. 그대로 읽으면
"관계를 진단해서 화면에 상시로 띄운다"가 되고, 이건 절대 제약과 정면으로 부딪힌다.

### 3-1. 걸리는 것과 걸리지 않는 것

`CLAUDE.md` 는 이미 이 경계를 정의해 뒀다. **금지 대상은 관계를 규정하는 말이지
감정을 언급하는 것 전부가 아니다.**

| | 예시 | 이 기능에서 |
| --- | --- | --- |
| ✅ 감정 알아봄 | "서운해 보여요", "편안해 보여요" | **이게 기능이다** |
| ❌ 관계 규정 | "사이가 팽팽해요", "요즘 뜸해요", "권태기" | 출력 금지 |
| ❌ 사람 평가 | "예민하시네요", "무뚝뚝해요" | 출력 금지 |

명세의 대표 예시 **"서운해 보여요"는 감정 알아봄이라 통과한다.** 이 기능의 출력을
전부 이 성격으로 맞추면 절대 제약과 충돌하지 않는다.

### 3-2. "사랑끈이 팽팽해집니다"는 문구가 아니라 시각 컨셉으로 본다

원문의 `ex) 커플 싸울 때 → (가제) 사랑끈이 팽팽해집니다` 는 **문구 규격 세 가지를
동시에 어긴다.**

| | 규격 | "사랑끈이 팽팽해집니다" |
| --- | --- | --- |
| 길이 | 10자 이하 | 11자 |
| 어미 | ~여요 / ~요 / ~해요 | ~니다 |
| 대상 | (3-1 표) | **두 사람의 관계**를 서술한다 |

같은 명세 표에 "디자인 컨셉 확정 후 시안 반영"이 적혀 있고 문구에는 `(가제)` 가 붙어 있다.
**문장이 아니라 컨셉 스케치로 읽는 게 맞다고 봤다.**

> ### 워커 노트 — 그림은 남고, 그림에 붙는 글자는 안 된다
>
> **①번 줄이 상시로 뜨는 것은 확정이다** (2장). 워커가 정할 문제가 아니라 이미 정해진
> 화면이다. 남은 문제는 그 줄을 **무엇으로 보여주는가**다 — 여기서 워커가 지킬 선은
> 하나다. **그림에 글자를 붙이지 않는다.**
>
> "권태기예요"라는 문장은 사용자 머릿속에 그 단어를 심지만, 팽팽해진 실 그림은
> 단어를 주지 않는다. 절대 제약의 근거가 "그 말을 들으면 의식이 심해진다"이므로
> 그림과 문장은 위험도가 다르다. 다만 실 옆에 "팽팽함" 같은 라벨이 붙는 순간
> 그림이 문장이 되고 제약이 그대로 깨진다.
>
> 그래서 워커가 내보내는 것을 이렇게 갈랐다.
>
> | | 워커가 내보내는 것 | 소유 |
> | --- | --- | --- |
> | ①번 줄의 글자 | 10자 문구. **상대방의 감정**까지만, 관계를 서술하지 않는다 | 워커 (하드 검증) |
> | ①번 줄의 생김새 | `emotionType`(라벨 5종) · `intensityValue` — **값만** | 프론트·디자인 |
>
> **워커는 그 수치에 이름을 붙여 내보내지 않는다.** 상태명·단계명·게이지 라벨 전부
> 해당한다. 필요해 보이면 만들지 말고 11장에 올린다.

### 3-3. 상시 노출은 위반 확률을 곱한다

말투 교정은 게이트가 걸린 요청에서만 문장을 만든다. 이 기능은 **매 요청 만든다.**
위반 확률이 1000분의 1이어도 하루 수백 번 뜨는 자리라면 반드시 나온다.
**"프롬프트로 잘 막으면 된다"가 성립하지 않는 자리다.** 6장의 근거다.

### 3-4. 하드 필터의 사각지대 — 지금 구조로는 검사되지 않는다

`worker/filter.py` 의 `visible_texts()` 는 **`AiResult` 의 `resultData` 만** 본다.

```python
def visible_texts(result: AiResult) -> list[str]:
    data = result.result_data
    if isinstance(data, ToneResultData): ...
```

이 기능의 문구를 `emotionAnalyses` 에 실으면 **하드 필터를 그냥 통과한다.**
`CLAUDE.md` 가 세그먼테이션에서 화제 라벨을 안 만든 이유와 정확히 같은 함정이다 —
"`filter.py` 는 `AiResult` 의 화면 문자열만 검사해서 안 걸러진다."

**필터 확장은 이 기능의 선택 사항이 아니라 전제 조건이다** (10장).

## 4. 명세 내부 충돌 3건과 처리

### ① "커플 양측 동일 노출" vs "상대방의 상태"

대상 칸은 **전체 (커플 양측 동일 노출)** 인데, 사용자 스토리는 **"상대방의 현재 감정"**
을 보여준다고 한다. 상대방 기준이면 A 화면과 B 화면의 **내용이 다르다.**

**"동일 노출"이 아니라 "대칭 노출"로 해석했다.** 양쪽 다 한 줄이 뜨고, 각자 상대의 상태를
본다. 근거 두 가지:

- 기능 부제가 **"상대방 감정 showing"** 이다. 내 감정을 나에게 보여주는 건 기능이 아니다
- 규격서 11장이 `subjectParticipant`(감정의 주인)와 `viewerParticipant`(보는 사람)를
  **따로** 두고 있다. 두 값이 같을 필요가 없게 설계된 자리다

```
A 화면 상단  "서운해 보여요"      ← subject=USER_B, viewer=USER_A
B 화면 상단  "편안해 보여요"      ← subject=USER_A, viewer=USER_B
```

이건 `CLAUDE.md` 의 "위젯은 사람마다 다르게 보인다"와도 맞는다. 다만 **`INDIVIDUAL`
카드와 성격이 다르다** — 개별 카드는 상대가 그런 게 떴다는 사실 자체를 몰라야 하지만,
이 한 줄은 양쪽 다 하나씩 갖는다. 숨기는 게 아니라 각자 다른 것을 본다.

> ### 🔄 기획 변경 (2026-08-19) — 대칭 노출 → **커플 공통 상태**
>
> PM 이 "둘의 상황 하나를 두 화면에 같게" 로 바꿨다. 위의 대칭 노출 해석은 이 시점까지의
> 기록으로 남긴다. 반영 방식:
>
> - **규격 무변경.** `subject`/`viewer` 두 항목을 그대로 내보내되 **라벨·강도·문구가
>   동일**하다. 백엔드 분배(viewer 필터)도 프론트 렌더링도 그대로 동작한다
> - **병합은 화자별 유효 점수의 축별 최댓값** (`state.read_state`). 평균이면 한쪽의
>   분노 4 가 상대의 평온 0 에 희석돼 임계 아래로 내려간다 — 갈등 신호가 사라진다.
>   반어 방어(`ANGER_WINS`)도 최댓값이라야 산다
> - 화자 단위 안전 규칙(애정 바닥값 · confident 게이트 · 미채점 무시)은 병합 **전에**
>   그대로 적용 — 근거 없는 감정을 지어내지 않는 원칙 유지
> - `shouldShow` 는 항상 `true` 가 됐다 — 한쪽이 침묵해도 다른 쪽 발화가 둘의 상황의
>   근거다. `trigger_message_ids` 도 대화 전체 id 로 넓혔다
> - **절대 제약 경계는 그대로다.** 문구는 여전히 감정 알아봄("서운해 보여요")이고
>   관계 규정("사이가 서먹")이 아니다 — 3-1 표의 문구 사전을 안 바꿨기 때문이다
> - 실측: `case11` 둘 다 "감정이 올라와요", `case18` 둘 다 "다정해 보여요",
>   `case2` 는 한쪽 활기 3 이 병합돼 둘 다 "신나 보여요" — STABLE 시연 대본은
>   더 밋밋한 문장으로 교체했다 (`demo-checklist.md` 4-1 막 1)

### ② "누적 추이" vs 무상태 REST

명세는 **"누적 감정 상태의 변화 추이 (쌓임 → 풀어짐)"** 를 요구한다. 그런데 워커는
동기 REST 요청마다 상태가 없고, 요청 페이로드에 과거 감정값이 들어오지 않는다.
`docs/server-handoff.md` 의 `recentResults` · `speakerProfiles` 와 **똑같은 문제**다.

- **MVP** — 요청에 들어온 스트림 안에서만 추이를 본다. 활성 세그먼트와 그 직전 맥락을
  함께 넣고 "쌓이는 중 / 풀리는 중 / 그대로"를 묻는다. 요청 경계를 넘는 추이는 못 본다
- **정식** — 서버가 직전 감정값을 요청에 실어준다 (9장, 규격 변경 요청 3번)

### ③ "감정 중재와 분리" vs 이미 있는 감정 판정

명세는 감정 중재와 본 기능을 분리하라고 못박았다. 그런데 `worker/tone.py` 의
`ToneJudgeLLMOutput` 은 이미 `emotion: calm / irritated / angry / hurt` 를 산출한다.
재사용하고 싶어지지만 **재사용하면 안 된다.**

| | 말투 교정의 emotion | 실 상태 표현 |
| --- | --- | --- |
| 언제 | 룰 게이트가 걸린 요청에만 | 매 요청 |
| 누구 | 문제 표현을 **보낸 사람** 1명 | **두 사람 각각** |
| 왜 | 대체 문장을 쓰기 위한 재료 | 그 자체가 출력 |

**사용자 스토리 [개별]이 이 분리를 그대로 설명한다** — "말투는 평범한데 상대가 서운해하는
것 같다". 말투 게이트가 안 걸리는 구간이 정확히 이 기능의 자리다.
게이트에 종속시키면 명세가 원하는 케이스가 통째로 사라진다.

## 5. 어디로 내보낼 것인가 — `emotionAnalyses` 다

두 가지 길이 있다. **규격서 11장 `emotionAnalyses` 를 채우는 쪽으로 결정했다.**

| | 4번째 `resultType` 신설 | **`emotionAnalyses` 채우기 (채택)** |
| --- | --- | --- |
| 규격 변경 | `resultType` enum + `resultData` 구조 신설 | **필드 2개 추가** |
| 화면 자리 | `results` 배열 = **②번 줄**과 섞인다 | 별도 배열 = **①번 줄과 1:1** |
| 대상 표현 | `visibilityType` 로는 대칭 노출을 못 쓴다 | `subject`/`viewer` 가 이미 있다 |
| 서버 역할 | 새로 정의 | 2장에 이미 있다 — "감정 분석 결과 생성/저장" |
| 상시성 | 카드 3종과 같은 배열에 섞여 우선순위가 꼬인다 | 분리돼 있어 안 꼬인다 |

**화면이 두 줄이면 배열도 두 개인 게 맞다.** `results` 는 ②번 줄, `emotionAnalyses` 는
①번 줄이다. 한 배열에 섞으면 프론트가 매번 `resultType` 을 보고 어느 줄인지 갈라야 하고,
"②는 비었는데 ①은 차 있다"는 정상 상태를 표현하기 어려워진다.

**규격서는 이 기능의 자리를 이미 비워 두고 있었다.** 11장 예시가 그대로 이 명세다.

```json
{
  "subjectParticipant": "USER_A",
  "viewerParticipant": "USER_B",
  "emotionType": "ANGER",
  "intensityValue": 4.0,
  "shouldShow": true,
  "triggerMessageIds": [101],
  "expiresAt": null
}
```

`emotionType` + `intensityValue` 가 명세의 "감정 수치 스코어링(Sadness 3점)"이고,
`subject`/`viewer` 가 4장①의 대칭 노출이다. **`docs/server-handoff.md` 에서 "명세가
아직 없어 `[]` 로 보낸다"고 답한 그 배열이 이 문서로 채워진다.**

### 모자란 것 — 화면 문구를 실을 자리가 없다

11장에는 **문구 필드가 없다.** 산출된 라벨을 문장으로 바꾼 결과를 담을 곳이 필요하다.
필드를 추가하지 않으면 프론트가 `emotionType` → 문구 매핑을 직접 들고 있어야 하는데,
그러면 **절대 제약을 지키는 문자열의 소유가 워커 밖으로 나간다.** 하드 필터가 검사할 수
없는 자리에 화면 문구가 생긴다 (3-4). 그래서 워커가 실어 보내는 쪽을 제안한다.

→ 규격 변경 요청 4건은 9장.

## 6. 문구를 누가 쓰는가 — LLM 이 아니라 고정 사전

**LLM 은 감정 점수까지만 낸다. 라벨은 룰이, 화면 10자는 사전이 정한다.**

이건 이 레포에서 이미 두 번 쓴 패턴이다.

| 기능 | LLM 이 하는 것 | LLM 이 하지 않는 것 |
| --- | --- | --- |
| 대화 분절 | 발화별 연속성 **점수** | 경계 결정 — 룰 임계값이 한다 |
| 데이트 코스 | 검색어·추천 이유 | 상호명·링크 — 카카오가 준 것만 쓴다 |
| **실 상태 표현** | **감정 4축 점수 (0~5)** | **라벨 — 임계값이 정한다 / 문구 — 사전에서 고른다** |

근거:

- **위반 확률이 곱해지는 자리다** (3-3). 상시 노출에서 자유 생성은 절대 제약을 상시로
  노출시킨다. 사전이면 위반 확률이 **0** 이다 — 문자열이 유한하고 미리 검사할 수 있다
- **10자와 어미 제약을 구조적으로 보장한다.** 생성이면 매번 세고 잘라야 하는데,
  10자를 자르면 문장이 깨진다
- **문구의 주인은 PM·디자인이다.** `worker/copy.py` 주석이 이미 그렇게 적고 있다.
  "디자인 컨셉 확정 후 시안 반영"이면 사전만 교체하면 되고 프롬프트를 다시 쓸 일이 없다
- **결정적이다.** 같은 대화에 항상 같은 문구가 나온다. 시연에서 재현된다
- **싸다.** 출력 토큰이 라벨 몇 개로 줄어 상시 호출의 비용이 내려간다

단점은 표현 다양성이다. 라벨당 문구를 2~3개 두고 `messageId` 기준으로 결정적으로
고르면 완화된다 (무작위는 쓰지 않는다 — 재현이 깨진다).

### 문구 사전 — 5종 확정 (디자인, 2026-08-17)

**감정 5종과 실 모양·글로우가 확정됐다.** 워커는 이 표의 `상태 라벨` 하나를 고르는 일만 한다.

| 상태 라벨 | 감정 | 실 모양 | 글로우 | 문구 | 자수 |
| --- | --- | --- | --- | --- | --- |
| `STABLE` | 평온 / 기본 | 아래로 축 늘어진 곡선 | 없음 (무채색) | 평온해요 | 4 |
| `RESOLVED` | 애정 / 설렘 | 중앙에 하트 매듭 | 핑크·마젠타 | 다정해 보여요 | 7 |
| `ACCUMULATED` | 서운함 / 오해 | 중앙이 엉킨 매듭 | 파랑 | 서운해 보여요 | 7 |
| `ENGAGED` | 들뜸 / 활기 | 크고 규칙적인 파동 | 초록 | 신나 보여요 | 6 |
| `ESCALATED` | 분노 / 격앙 | 날카롭고 좁은 스파이크 | 빨강 | 감정이 올라와요 | 8 |

> ### 워커 노트 — 확정안이 설계를 한 단계 단순하게 만들었다
>
> 초안은 **감정 7종 × 추이 3종**의 격자였다. 확정안은 그 두 축이 **하나로 합쳐져 있다** —
> `RESOLVED`(풀어짐) · `ACCUMULATED`(쌓임) · `ESCALATED`(격해짐)가 추이를 라벨 안에
> 이미 담고 있다. 그래서:
>
> - **`trend` 필드가 통째로 사라진다.** 9장에서 뺐던 판단이 확정안으로 확인됐다
> - **사전이 5줄이다.** 초안 13줄에서 줄었고, 5종 전부 실 모양과 1:1이라 화면과 안 어긋난다
>
> `ANXIETY`(불안·걱정)는 확정안에 없다. 5종에 접어 넣는다 — 관계 맥락의 걱정은
> `ACCUMULATED`, 그 외에는 `STABLE`. **없는 라벨을 워커가 만들지 않는다.**

### 라벨은 LLM 이 고르지 않는다 — 감정 점수에서 룰이 정한다

**처음에는 LLM 에게 라벨 5종 중 하나를 직접 고르게 했다. 실측에서 깨졌다** (12장).

`case11_mixed` 에서 **말투 교정은 공격 표현(`generalization`)으로 잡은 발화를, 상태 산출은
서운함(`ACCUMULATED`)으로 읽었다.** 3회 반복에서 전부 그랬다. 한 발화를 두 기능이 다르게
읽는 것이고, **라벨이 LLM 안에 있으니 조정할 손잡이가 없었다** — 프롬프트를 다시 쓰는 것
말고 할 수 있는 게 없다.

**분절에서 경계를 LLM 밖으로 뺀 이유와 똑같다.** 명세의 산출 흐름도 원래 이쪽이다 —
"감정 수치 스코어링(예: Sadness 3점) → 상태 라벨 매핑".

```
LLM     화자마다 감정 4축 점수      애정 0~5 · 서운 0~5 · 활기 0~5 · 분노 0~5
  ↓
룰      pick_label()               임계값으로 라벨 1개
  ↓
사전    copy.STATE_TEXT            문구 10자
```

| 축 | 라벨 | |
| --- | --- | --- |
| `affection` | `RESOLVED` | 쌓인 것이 **풀리는** 흐름 |
| `hurt` | `ACCUMULATED` | 안으로 **쌓이는** 흐름 |
| `joy` | `ENGAGED` | |
| `anger` | `ESCALATED` | 밖으로 **터뜨림** |
| *(없음)* | `STABLE` | 네 축이 전부 임계 아래 |

**`STABLE` 에 해당하는 축을 두지 않는다.** 처음엔 `calm` 축을 뒀는데 모델이 그걸
바닥값으로 깔아서(전 픽스처에서 3점) 다른 축이 3 이하면 전부 `STABLE` 로 먹혔다.
평온은 다른 감정이 없는 상태지 경쟁하는 감정이 아니다.

임계값 네 개가 손잡이다.

| 상수 | 값 | 뜻 |
| --- | --- | --- |
| `MIN_SCORE` | 3 | 최고점이 이 아래면 `STABLE`. **프롬프트 앵커("3 = 뚜렷하다")에 맞췄다** |
| `ANGER_WINS` | 3 | `anger` 가 이 이상이면 다른 축보다 낮아도 `ESCALATED` |
| `PRIORITY` | anger→hurt→joy→affection | 동점일 때의 순서 |
| `AFFECTION_WORDS` | "사랑"·"보고싶"·"보고 싶" | 직전 발화(`AFFECTION_RECENT`=3개)에 있으면 `affection` 을 `MIN_SCORE` 까지 바닥값 보정 |

**`AFFECTION_WORDS` 는 연동 실측이 만든 룰이다** (2026-08-19). "사랑해" 같은 짧은 애정
발화의 `affection` 을 LLM 이 2 이하로 깔면 `MIN_SCORE` 에 걸려 `STABLE` 이 떴다.
**바닥값이지 강제 라벨이 아니다** — 보정 뒤 판정은 그대로 `pick_label()` 이 해서 반어
("사랑 같은 소리 하네")는 분노 점수가 막고, `confident=false` 도 낱말이 있으면 넘는다
(낱말 자체가 프롬프트가 요구하는 "문장으로 짚을 수 있는 근거"다). 창 전체가 아니라
직전 발화만 보는 이유: 창이 미끄러지는 동안 대화 초반의 "사랑해" 하나가 계속 바닥값을
만들면 상태가 지금을 안 보여준다. "사랑니"는 지우고 보고, "영화 보고싶어"(콘텐츠)는
못 가른다 — 틀려도 긍정 방향이라 없던 갈등을 만들지는 않는다.
검증 픽스처는 `fixtures/case18_affection.json`.

**`ANGER_WINS` 가 `case11` 을 고친 값이다.** 분노는 혼자 오지 않는다 — 서운해서 화가
난다. 그래서 다투는 구간은 `hurt` 와 `anger` 가 같이 높고, 최고점만 보면 서운함이 이겨서
파란 매듭이 뜬다. 화면에 필요한 건 "지금 격해졌다"는 신호고 그게 빨간 스파이크의 자리다.
**보수적으로 가려면 이 값을 올리면 된다 — 프롬프트를 고칠 필요가 없다.**

`PRIORITY` 에서 `joy` 를 `affection` 보다 앞에 둔 이유: `RESOLVED`(감정 풀어짐)는 쌓인
것이 있었을 때만 뜻이 있는 라벨이다. 데이트 계획처럼 애정과 활기가 같이 높은 자리에서
"다정해 보여요"가 뜨면 화해한 것처럼 읽힌다 (`case9_date` 가 실제로 그랬다).

#### `ESCALATED` 문구 교체 기록 (2026-08-17 확정)

최초 확정안은 **"많이 화났어요"** 였고, 검토 중 **"감정이 올라와요"** 로 바꿨다.
5개 중 이것만 명세 자체의 제약과 부딪혔기 때문이다.

| | |
| --- | --- |
| 명세 제약 | "**단정·판단형 표현 금지**" |
| 최초 문구 | "많이 화났어요" — 5개 중 유일한 **단정형**, 강도를 말로 키운다 |
| 확정 문구 | "감정이 올라와요" — 추측·관찰형. `CLAUDE.md` 의 허용 예시를 줄인 것 |

`ESCALATED` 가 뜨는 순간은 대개 **말투 교정이 같이 발동하는 순간**이다. A 화면 ②줄에는
교정 제안이 뜨고, B 화면 ①줄에는 상태 문구가 뜬다. 여기서 "화가 났다"고 단정해서 상대에게
알려주면 B 는 방어적으로 반응하고 **개입이 갈등을 키우는 방향으로 돈다.**
나머지 4개는 확정안 그대로 쓴다.

> 문구를 지을 때 **글자 수를 먼저 센다.** "화가 많이 났나 봐요"처럼 자연스러운 표현이
> 11자로 규격을 넘는다. 5개 전부 10자 이하·`~요` 체·`filter.BANNED` 미포함을 검산했다.

**문구만 정해 주시면 됩니다.** 워커 쪽 로직은 어느 쪽이든 동일합니다.

문구 작성 규칙 (사전을 늘릴 때 지킬 것):

1. **주어는 상대방의 감정이다.** 두 사람의 관계가 주어가 되면 안 된다 (3-1)
2. **사람을 평가하지 않는다.** "예민해요"(X) / "감정이 올라와요"(O). 말투 교정의
   "대상이 사람이면 안 되고 말이면 된다"와 같은 원칙이다
3. **추측 표지를 쓴다.** `~보여요` · `~나 봐요`. 명세의 "단정·판단형 표현 금지"다.
   틀렸을 때 "아닌데?"로 넘길 수 있는 문장이어야 한다
4. **강도에 비례해 세지지 않는다.** 강도 5라고 "많이 화났어요"로 올리지 않는다 —
   격한 순간에 상대의 화를 크게 알려주면 갈등을 키운다. 강도는 수치로만 나간다
5. 10자 이하 · `~여요 / ~요 / ~해요` 체

> ### 워커 노트 — 사전을 임포트 시점에 검증한다
>
> 문구가 상수라는 것은 **미리 전부 검사할 수 있다**는 뜻이다. `copy.py` 로드 시점에
> 사전 전체를 훑어 ① 10자 이하 ② 어미 화이트리스트 ③ `filter.BANNED` 미포함을 확인한다.
> PM 이 문구를 바꿔도 규격 위반이면 그 자리에서 터진다. 화면에 나간 뒤에 발견하지 않는다.

## 7. 산출 파이프라인

```
활성 세그먼트(ctx.active) + 직전 맥락
   ↓
state.read_state()          LLM 1회 — 화자별 감정 4축 점수 (라벨도 문구도 없음)
   ↓
state.pick_label()          룰 — 임계값으로 라벨 1개 + 강도
   ↓
룰 — 근거 검증               해당 화자의 발화가 없으면 중립 유지 (shouldShow=false)
   ↓
copy.STATE_TEXT[라벨]        문구 선택 (LLM 아님)
   ↓
emotionAnalyses[]           viewer 별 1건씩, 최대 2건
```

### 보는 범위

`CLAUDE.md` 의 "맥락과 트리거를 갈라 쓴다" 표에 한 줄이 추가된다.

| | 보는 범위 |
| --- | --- |
| 게이트 · 트리거 id · RAG · 기억 추출 | `ctx.active` |
| 말투 판정 프롬프트의 직전 대화 | `ctx.context` |
| 말투 기준선 (`profile.py`) | `ctx.messages` |
| **실 상태 표현** | **`ctx.context`** — 활성 세그먼트 + 부족분만 앞에서 채움 |

활성 세그먼트만 보면 **추이를 볼 수 없다.** "쌓임 → 풀어짐"은 최소 두 시점이 필요하다.
말투 판정이 같은 이유로 쓰는 `ctx.context` 를 그대로 쓴다 — 새 범위를 만들지 않는다.

전체 스트림(`ctx.messages`)을 쓰지 않는 이유는 분절 설계 그대로다. 세 시간 전에 끝난
다툼의 감정을 지금 화면에 띄우면 늦은 게 아니라 **틀린 것**이다.

**다만 창 전체를 채점 대상으로 주지는 않는다** (2026-08-20 배포 QA8 실측). 격한 싸움 뒤
화해 6건 + 화제 전환 4건을 쌓아도 `ESCALATED` 가 안 내려왔다 — 같은 세그먼트 안에 싸움
발화가 남아 있는 한 프롬프트 앵커("3 = 로그에서 문장으로 짚을 수 있다")에 분노가 계속
걸렸고, "뒤쪽이 근거"라는 지침만으로는 안 지켜졌다. 그래서 분절 채점(`segment._transcript`)
과 같은 구획 분리를 쓴다: **채점 대상은 마지막 `SCORE_RECENT`(6)개**, 그 앞은
"흐름만 — 채점 금지" 구획으로 넘긴다. 추이는 여전히 읽힌다(앞 구획이 흐름을 보여준다) —
인용만 못 하게 한 것이다. 발화 유무 게이트와 `AFFECTION_WORDS` 바닥값도 채점 구간
기준으로 함께 좁혔다 — 창 밖 발화로 기여 자격을 만들면 제한이 새로 샌다.
검증: `fixtures/case19_washout.json`(씻김) + case7(즉시 감지)·case18(애정 룰)·case2(평온)
회귀 통과 (2026-08-20).

### 중립이 기본값이다

명세는 "항상 출력"이지만, **근거가 없을 때 감정을 지어내면 없던 갈등을 만든다.**
B 가 "ㅇㅇ" 한 마디만 한 요청에서 "서운해 보여요"가 뜨면, A 는 있지도 않은 서운함에
반응하기 시작한다. 데이트 코스가 없는 발화를 인용하지 않는 것과 같은 이유다.

| 상황 | 처리 |
| --- | --- |
| 근거가 충분 | 해당 라벨 + `shouldShow: true` |
| 그 화자의 발화가 활성 맥락에 없음 | `STABLE` + `shouldShow: false` (프론트는 직전 문구 유지) |
| 신호가 약함 / 확신 없음 | `STABLE` — "평온해요" |
| LLM 호출 실패 | 해당 요청은 배열을 비운다. 문구를 지어내지 않는다 |

`shouldShow` 를 **"이번 요청에서 문구를 갱신할지"** 로 정의하면 "항상 화면에 뭔가 떠
있다"(명세)와 "근거 없이 지어내지 않는다"(워커 원칙)를 동시에 만족한다.
화면은 비지 않고, 값은 갱신되지 않는다.

### 값 정의 제안 (규격서 11장 "추후 확정")

| 필드 | 값 |
| --- | --- |
| `emotionType` | `STABLE` `RESOLVED` `ACCUMULATED` `ENGAGED` `ESCALATED` **5종 확정** |
| `intensityValue` | `0.0` ~ `5.0` (명세 "Sadness 3점", 규격서 예시 `4.0` 과 정합) |
| `stateText` *(추가 요청)* | 화면 문구. 10자 이하 |
| `shouldShow` | 위 정의 |
| `triggerMessageIds` | 판정 근거가 된 활성 맥락의 메시지 id |
| `expiresAt` | **마지막 메시지 + 3시간** |

`emotionType` 에 **감정 이름(`Calm`·`Anger`…)이 아니라 상태 라벨을 넣는다.** 디자인 표의
`State Label` 이 이미 대문자 스네이크로 코드값처럼 적혀 있고, 실 모양과 1:1 이라 프론트가
받아서 바로 쓸 수 있는 축이 이쪽이다. 감정 이름 쪽(`Calm / Neutral`)은 슬래시가 들어가
enum 이 되지 않는다. **필드 이름은 `emotionType` 인데 값은 상태 라벨**이라는 어긋남만
서버에 한 줄 설명한다 (9장).

`intensityValue` 는 문구를 세게 만드는 데 쓰지 않는다 (6장 규칙 4). 글로우 세기·파동
진폭·스파이크 날카로움처럼 **실의 강약**에만 쓰이는 값이다.

`expiresAt` 을 3시간으로 잡은 근거는 새로 정한 게 아니다. `segment.py` 의 `GAP_HARD`
가 이미 "3시간 이상 벌어지면 다른 대화"로 쓰고 있다. 같은 기준을 쓰면 만료된 상태 문구가
새 세그먼트로 넘어가지 않는다. **워커가 "안 나눈다"고 판단하는 구간과 프론트가 "아직
유효하다"고 보는 구간이 어긋나면 안 된다.**

## 8. 파이프라인 배치와 비용

```
split()          분절                    LLM 1회  ← 반드시 먼저
   ↓
router.run()  ┬─ read_state()   실 상태    LLM 1회  ← 추가
              ├─ 말투 판정 → 말투 생성
              └─ harvest_memories() → 데이트 계획 → 카카오 → 데이트 문구
                                       └─ 유튜브 (말투 결과를 본 뒤)
```

**분절 다음에 놓는다.** 활성 맥락이 정해져야 무엇을 읽을지 정해진다.
**기억 추출·말투 판정과 나란히 놓는다.** 서로 결과를 쓰지 않으므로 순서가 없다.

### 비용

매 요청 고정 LLM 호출이 2회 → **3회**가 된다. `docs/server-handoff.md` 에서 타임아웃
30초를 제안하며 정리한 표에 한 줄이 추가되는 셈이다.

**상태 산출은 기억 추출·말투 판정과 동시에 돈다** (`router.run()`). 셋이 서로 결과를 쓰지
않아서 호출이 하나 늘어도 벽시계는 거의 그대로다 — 실측에서 요청당 **16~32% 단축**됐다.

**분절 호출에 합치지 않는다.** 분절 출력에 필드를 하나 더 얹으면 출력 토큰이 늘고,
그게 그대로 지연이 된다 — 근거 문구(`note`) 한 줄을 뺐더니 4.0초가 2.3초가 됐다
(1부 9장). 같은 실수를 반대 방향으로 하지 않는다.

**폴백이 워커를 죽이지 않는다.** 상태 산출 실패는 오류가 아니라 "이번엔 갱신 없음"이다.
`segment.py` 의 `_score()` 가 실패를 `None` → 안 나눔으로 처리하는 것과 같은 방식이다.

## 9. 서버에 알릴 것 — **규격 변경 없음.** 동작 확인 2건 + 통보 1건 + 제안 1건

> 📄 **전달 문서는 `docs/server-handoff.md` 다.** 서버 담당자가 그것만 읽으면 되도록
> 자체 완결로 썼다. 이 장은 **왜 그렇게 정했는지**를 남기는 자리다.

**`emotionAnalyses` 로 충분하다.** 새 `resultType` 도, 새 배열도, **필수 필드 추가도 없다.**
규격서 11장이 이 기능의 자리를 이미 비워 뒀고, `docs/server-handoff.md` 에서 "명세가
나오면 채우겠다"고 답해 둔 그 자리다. **협의는 사실상 끝나 있다.**

| | 항목 | 성격 |
| --- | --- | --- |
| 🔴 1 | `SKIPPED` 가 사실상 사라진다 | **동작 변경.** 전송을 건너뛰면 ①번 줄이 영영 안 뜬다 |
| 🔴 2 | `emotionAnalyses` 도 `viewerParticipant` 로 갈라서 전송 | **동작.** 안 가르면 A 화면에 B 것이 뜬다 |
| 🟢 3 | `emotionType` 5종 · `intensityValue` 0~5 · `expiresAt` 3시간 | **통보.** 규격서가 "추후 확정"으로 비워둔 칸을 채우는 것 |
| 🔵 4 | `emotionAnalyses[].stateText` (String, **선택**) | **제안.** 안 받아도 그만이다 |

**🔴 두 개가 전부 필드가 아니라 동작이다.** 규격서 대조만으로는 드러나지 않는다 —
스키마는 그대로인데 서버가 그걸 어떻게 다루느냐가 바뀐다. 그래서 전달 문서 앞머리에 뒀다.

2번은 `results` 의 `INDIVIDUAL` 을 `targetParticipant` 로 가르는 것과 같은 규칙인데
**가르는 키가 다르다** (`visibilityType`/`targetParticipant` → `viewerParticipant`).
방 단위로 브로드캐스트하면 A 가 자기 자신의 상태를 보게 되고, "상대방 감정 showing"이라는
기능의 의미가 통째로 뒤집힌다.

### 🟢 3 — 값 정의 통보

7장 표대로 보낸다. 한 가지만 설명이 필요하다 — **필드 이름은 `emotionType` 인데 값은
상태 라벨**(`STABLE` · `RESOLVED` · `ACCUMULATED` · `ENGAGED` · `ESCALATED`)이다.
디자인 확정안의 축이 이쪽이고 실 모양과 1:1 이라 그렇다 (7장). 서버는 이 값을 저장만
하면 되고 해석할 일이 없다.

`category` enum 때와 같은 사고를 막으려는 통보다 — 워커가 보내는 값이 규격에 없어
응답 검증에서 반려되는 상황.

### 🔵 4 — 문구 필드는 이제 "있으면 좋은 것"으로 내렸다

초안에서는 이걸 🔴 필수로 잡았었다. **디자인 확정안이 나오면서 근거가 약해졌다.**

확정 표는 `상태 라벨 → 실 모양 · 글로우 · 문구`가 **한 표에 묶여 있고, 프론트는 이 표를
어차피 구현해야 한다** (실 모양과 글로우 때문에). 문구 열만 워커가 따로 실어 보내면
같은 표가 두 군데로 쪼개진다.

| | 워커가 보낸다 (`stateText`) | 프론트가 표를 갖는다 |
| --- | --- | --- |
| 서버 작업 | String 컬럼 1개 | **없음** |
| 절대 제약 | 하드 필터가 검사한다 | 문구가 **고정 5개**라 1회 리뷰로 끝난다 |
| 표의 일관성 | 문구만 다른 곳에서 온다 | **한 표에 모여 있다** |
| 나중에 | 라벨당 문구 변형·상황별 조정이 가능 | 라벨 1개 = 문구 1개로 고정 |

**절대 제약 논거가 여기서는 약하다.** 하드 필터가 지키려는 것은 매 요청 새로 생기는
문자열(LLM 생성물, 유튜브 제목)이다. 문구가 **상수 5개**면 화면에 나가기 전에 사람이
한 번 읽으면 끝난다 — `copy.py` 의 `TONE_GUIDE` 와 같은 성격이다.

그래서 **선택 필드로 제안하고, 안 받아주면 그냥 생략한다.** 규격서 14장의 "선택 필드에
값이 없으면 필드 생략"을 그대로 따르면 되고 `videoSummary` 와 같은 처지가 된다.
**어느 쪽이든 워커 로직은 같다** — 사전은 `copy.py` 에 두고 devui·트레이스에서 쓴다.

> ### 워커 노트 — 요청 4건에서 0건까지 내려온 경위
>
> | | 왜 뺐나 |
> | --- | --- |
> | `trend` 필드 | 확정안의 `RESOLVED`·`ACCUMULATED`·`ESCALATED` 가 추이를 **라벨 안에 이미 담고 있다.** 별도 축이 필요 없다 |
> | 요청 `previousEmotions` | 있으면 요청 경계를 넘는 추이가 정확해지지만, 없어도 스트림 안에서 판단된다(4장②). **정확도 문제지 구현 가능 여부가 아니다** |
> | `stateText` 필수 → 선택 | 위 |
>
> `recentResults` · `speakerProfiles` 는 **없으면 규칙 자체가 구현 불가**라 🔴 였다.
> 이번 것들은 성격이 다르다. **서버에 던지는 요청이 많아질수록 정말 필요한 그 두 개가 묻힌다.**

### 🔴 1 — `status` 가 사실상 항상 `COMPLETED` 가 된다

규격서 12장은 `COMPLETED` 를 "기능 결과 **또는 감정 분석 결과**가 존재"로 정의한다.
이 기능이 상시 작동하면 `emotionAnalyses` 가 매번 차므로 **`SKIPPED` 는 거의 나오지
않는다** — 상태 산출까지 실패했을 때만 남는다.

지금 `worker/pipeline.py` 는 `results` 가 비면 `SKIPPED` 를 돌려준다. 이 로직이 바뀐다.
**서버가 `SKIPPED` 를 "아무것도 안 함"으로 보고 전송을 건너뛰고 있다면 한 줄 문구가
영영 안 뜬다.** 반드시 알려야 한다.

**문구가 아니라 라벨이 맞는지를 먼저 본다.**

| `case3_one_sided` | 리액션만 하는 쪽이 격한 라벨을 받지 않는다 | ✅ A 활기3 → `ENGAGED` / B 활기1 → `STABLE` |

`shouldShow: false` 는 **그 사람 발화가 활성 맥락에 아예 없을 때만** 나온다.
`case3_one_sided` 의 B 는 "ㅇㅇ" · "응" 같은 리액션이라도 발화가 있어서 `true` 다 —
이 픽스처로는 그 경로가 안 걸린다.

### 두 번 고쳤다 — 실측이 아니었으면 못 봤을 것들

전 픽스처의 라벨 분포와 반복 실행 흔들림을 재서 잡았다.

**① 라벨이 화자를 건너뛰었다.** `case7_tone` 의 B(사과하는 쪽)에게 `ESCALATED` 가 붙었고,
모델이 쓴 `note` 는 "격앙되지는 않았으나"였다 — **근거와 라벨이 서로 어긋나 있었다.**
대화 전체의 온도를 두 사람에게 똑같이 칠한 것이다.
→ `state.md` 에 "그 화자가 **직접 쓴 말만** 보고 채점한다" + "`note` 는 반드시 점수의
근거여야 한다"를 넣어 잡았다.

**② 말투 교정과 상태 산출이 한 발화를 다르게 읽었다.** `case11_mixed` 의 "너 맨날 이런
식이지"를 말투 게이트는 공격 표현으로 잡는데 상태는 `ACCUMULATED`(서운함) 3회 고정이었다.
같은 유형인 `case7` 의 "야 너는 맨날 그런 식이야"는 `ESCALATED` 였다 — **같은 화법이
케이스마다 다른 라벨을 받았다.**
→ 라벨을 LLM 밖으로 빼고 `ANGER_WINS` 임계로 잡았다 (6장).

| | 고치기 전 | 고친 뒤 |
| --- | --- | --- |
| `case11` A | `ACCUMULATED` ×3 | **`ESCALATED` ×3** — 말투 교정과 일치 |
| `case7` A | `ESCALATED` ×3 | `ESCALATED` ×3 |
| `case7` B | `STABLE` ×2 / `RESOLVED` ×1 (흔들림) | **`RESOLVED` ×3** (고정) |
| `case9` | `RESOLVED` (애정3 = 활기3 동점) | **`ENGAGED`** — 데이트 계획에 "다정해 보여요"는 화해로 읽힌다 |

### 라벨 분포 (전 픽스처 11개 × 2명 = 22건)

```
STABLE 12   ENGAGED 5   ESCALATED 2   ACCUMULATED 2   RESOLVED 1
```

**5종이 전부 나온다.** `STABLE` 이 55%인데, 픽스처 절반(`case1` · `case2` · `case4` ·
`case5` · `case6`)이 감정 신호가 없는 일상 잡담이라 그게 맞는 값이다 —
"평온해요"가 뜨는 게 정상인 대화들이다.

### 반복 안정성 (같은 입력 3회)

6개 케이스 중 **5개 고정.** `case10_concern` 의 B 만 `RESOLVED` ×2 / `ACCUMULATED` ×1 로
흔들리는데, 사과하면서 동시에 답답해하는 발화라 둘 다 타당하다.

### 상시 검사

문구는 `copy.STATE_TEXT` 상수 5개고 **임포트 시점에** 10자 · 어미 · `filter.BANNED`
미포함을 검사한다. 화면에 나간 뒤에 발견하지 않는다.

## 13. 프론트 연동 — 민상님께

워커가 내보내는 값과 화면 규칙만 정리했다. **`devui` 에 같은 구조를 구현해 뒀으니
동작을 보고 싶으면 그쪽을 켜면 된다** (`.venv/bin/python devui/server.py`).

### ①번 줄 — `emotionAnalyses` 에서 **내 것 하나**를 고른다

```js
const mine = res.emotionAnalyses.find(s => s.viewerParticipant === myKey);
```

배열에 2건이 들어 있다. `viewerParticipant` 가 **보는 사람**이다. 기획 변경(2026-08-19)
으로 두 건의 **라벨·강도·문구가 동일**하다 — 둘의 공통 상태 하나를 양쪽에 띄운다.
그래도 위 코드로 내 것을 고르는 게 맞다(구조는 안 바뀌었고, 앞으로 달라져도 안전하다).

> **필드가 8개지만 최소 2개만 읽으면 화면이 그려집니다** — `viewerParticipant`(내 것 고르기)
> + `emotionType`(실 모양·글로우·문구). 나머지는 필요해질 때 쓰면 되고, **안 읽어도
> 아무 문제 없습니다.** 8개인 이유는 규격서 11장이 원래 그 모양이라서지, 프론트가
> 다 다뤄야 해서가 아닙니다.
>
> 서버가 수신자별로 갈라 보내면 배열에 내 것 1건만 올 수도 있다. 그때도 위 코드는 그대로
> 동작한다.

| 필드 | 쓰는 법 |
| --- | --- |
| `stateText` | **화면에 그대로 출력한다.** 10자 이하 보장 |
| `emotionType` | 실 모양·글로우를 고르는 키. 아래 5종 |
| `intensityValue` | `0.0`~`5.0`. 글로우 세기·진폭 같은 **강약**에만 쓴다 |
| `shouldShow` | `false` 면 **직전 문구를 그대로 둔다.** 화면을 비우는 게 아니다 |
| `expiresAt` | 이 시각이 지나면 문구를 내린다 (마지막 메시지 +3시간) |
| `subjectParticipant` | 누구의 상태인지. 화면에 표시할 필요는 없다 |

| `emotionType` | 실 모양 | 글로우 | `stateText` |
| --- | --- | --- | --- |
| `STABLE` | 아래로 축 늘어진 곡선 | 없음 (무채색) | 평온해요 |
| `RESOLVED` | 중앙에 하트 매듭 | 핑크·마젠타 | 다정해 보여요 |
| `ACCUMULATED` | 중앙이 엉킨 매듭 | 파랑 | 서운해 보여요 |
| `ENGAGED` | 크고 규칙적인 파동 | 초록 | 신나 보여요 |
| `ESCALATED` | 날카롭고 좁은 스파이크 | 빨강 | 감정이 올라와요 |

`stateText` 는 **규격서에 없는 선택 필드**다. 서버가 저장·전달하지 않기로 하면 빠져서
올 수 있으니, **위 표를 프론트에도 넣어 두고 없으면 `emotionType` 으로 매핑**하면 된다.
라벨당 문구는 1개로 고정이라 매핑에 분기가 없다.

> ⚠️ **실 옆에 상태 이름을 글자로 붙이지 말아 주세요.** "팽팽함", "감정 쌓임", `ACCUMULATED`
> 같은 라벨이 화면에 글자로 뜨면 이 프로젝트의 절대 제약(`CLAUDE.md`)이 깨집니다.
> 그림은 괜찮고 글자가 안 됩니다 — 화면에 나가는 글자는 `stateText` 한 줄뿐입니다.
> 강도(`4.0`)도 숫자로 노출하지 않습니다.

### ②번 줄 — `results`

- **우선순위 순으로 정렬해서 보낸다.** 한 줄만 쓰면 `results[0]` 을 쓰면 된다
- 미발동이면 빈 배열이다. **빈 줄이 정상 상태다** — 오류가 아니다
- `visibilityType` 이 `INDIVIDUAL` 이면 `targetParticipant` 인 사람에게만 보여야 한다.
  **상대는 그런 게 떴다는 사실 자체를 몰라야 한다** (설계상 의도된 것)

### ②번 줄 카드를 언제 내리나 — 종류별 유지 창 부탁 (2026-08-20 배포 QA 발견)

현행 프론트(번들 실측)는 종류 구분 없이 **"트리거 메시지가 최근 15건 안 OR 생성 2분
이내"** 면 카드를 유지한다. 그래서 말투 교정 카드가 **대화가 장난 → "사랑해"로 넘어간
뒤에도 계속 떠 있었다** (실측: 트리거 뒤 새 메시지 7건, 여전히 표시 중). 교정은 "방금
보낸 그 메시지를 이렇게 바꿔보라"는 제안이라, 당사자가 다음 메시지를 보낸 순간 효용이
끝난다 — 남아 있으면 계속 혼내는 화면이 된다.

**종류별로 창을 갈라 주시길 제안합니다** (규격 변경 없음 — 이미 받는 필드만 쓴다):

| `resultType` | 메시지 창 (트리거가 최근 N건 안) | 시간 백스톱 |
| --- | --- | --- |
| `TONE_CORRECTION` | **3건** | **45초** (읽을 시간 보장) |
| `DATE_RECOMMENDATION` · `YOUTUBE_RECOMMENDATION` | 15건 (현행) | 2분 (현행) |

데이트·유튜브는 "이번 주말에 가자", "나중에 볼 영상"이라 길게 남는 게 자연스럽고,
교정만 짧아야 한다. 워커가 만료를 실어줄 수 없는 이유: 규격서의 `results` 에는
`expiresAt` 필드가 없고(①번 줄만 있다), 워커는 상태를 갖지 않아 "내려라" 신호를
따로 보낼 수도 없다 — **표시 수명은 프론트만 정할 수 있는 값이다.**

### 두 줄은 서로 밀어내지 않는다

3종이 전부 미발동이어도 ①번 줄은 남고, 데이트 카드가 떠도 ①번 줄이 밀려나지 않는다.
**②의 빈 줄은 정상이고, ①의 빈 줄은 사고다** — ①이 비면 워커 쪽 문제이니 알려 주세요.

### 확인 부탁드리는 것 2가지

1. **②번 줄이 한 줄이면 3종 동시 발동 시 하나만 뜬다.** 그러면 워커의 정렬 순서가 곧
   화면 선택이 된다. 이 해석이 맞는지 (11장 미결 3)
2. **`shouldShow: false` 일 때 직전 문구를 유지하는 동작**이 가능한지 (11장 미결 4)

# 3부. 기억/RAG 평가셋

> `tools/build_eval_set.py` — 외부 멀티세션 대화를 규격 형식으로 바꾼 2,000 케이스
>
> 원래 문서: `기억/RAG 평가셋 v1`

`extract.py` 가 뽑은 기억을 `retrieve.py` 가 제대로 찾아오는지 검증하기 위한 데이터셋.

빌더: `tools/build_eval_set.py` · 산출물: `data/eval/msd_sample.jsonl` (git 에 올리지 않는다)

---

## 왜 필요한가

기억 저장소와 RAG 는 데이트 코스 추천의 근거 전부다. 그런데 지금 이걸 검증할 데이터가
없다 — 손으로 쓴 시드 27건과 픽스처 10개가 전부이고, **둘 다 우리가 정답을 알고 만든
것이라 통과하는 게 당연하다.** "지난주에 마라탕 땡긴다고 하셨던 거 기억하고 골라봤어요"
가 처음 보는 대화에서도 나오는지는 확인된 적이 없다.

## 원본

[nayohan/141_korean_multi_session_dialogue](https://huggingface.co/datasets/nayohan/141_korean_multi_session_dialogue)
— AI Hub 141 주제별 텍스트 일상 대화. 76,000행 / 122MB / 주제 248종.

**두 사람이 시간을 두고 두 번 대화한다.** `session1` 에서 나온 이야기가 `session2` 에서
다시 언급되는 구조라 기억 검증에 그대로 맞는다. 이 성질 때문에 고른 데이터셋이다.

## ⚠️ 이 데이터로 하면 안 되는 것

**말투 기준선(`data/speaker_profiles.json`) 학습에 쓰지 않는다.**

원본은 **처음 만난 두 사람의 존댓말 대화**다. 커플 반말 채팅과 마침표율·호칭·ㅋ 개수가
전부 다르다. `profile.py` 는 "그 사람의 평소 대비 변화량"으로 판정하므로 기준선이 틀어지면
말투 교정 기능이 통째로 무너진다. 같은 이유로 이 데이터의 **말투 게이트 발동률을 오탐률로
읽어서도 안 된다** — 애초에 다른 종류의 대화다.

## 변환 규칙

| 원본 | 변환 결과 |
| --- | --- |
| `personaInfo_cl` | `USER_A` — 짝수 인덱스 발화자, 먼저 말한다 |
| `personaInfo_cp` | `USER_B` — 홀수 인덱스 발화자 |
| `session1` / `session2` | 규격서 5장 `AnalysisRequest` 2개 |
| session2 첫머리의 "3주만이네요" | `gapDays` — 두 세션의 시각 차이 |

원본은 각 칸이 파이썬 리스트 리터럴 **문자열**이라 `ast.literal_eval` 로 푼다.

**발화자 배정은 원본에 라벨이 없다.** 짝수 인덱스를 `personaInfo_cl` 로 가정했고,
전량 76,000행에 성별 대조를 돌려 73,027건 일치 / 192건 불일치로 확인했다. 불일치 행은
걸러낸다. 다만 **연속 발화가 하나로 합쳐진 행은 검출할 방법이 없다** — 남아 있을 수 있다.

### 시각

- `session2` 의 시작을 **2026-08-15 20:00 KST 로 고정**한다. 기억의 30일 중복 판정이
  케이스마다 다른 "지금"을 보면 결과가 재현되지 않는다.
- `session1` 시작 = 고정 시각 − `gapDays`
- 메시지 간격은 1~5분. 케이스 id 로 시드를 고정해 매번 같은 값이 나온다.

간격은 지어내지 않고 **원문에서 읽는다.** "3주만이네요"라고 말하는 대화가 하루 뒤로
찍히면 시점을 근거로 삼는 기억 추출이 그 불일치를 그대로 추천 이유로 내보낸다.
표현이 없는 경우(79%)만 기본값 7일을 쓴다.

## 품질 필터

| 사유 | 제외 |
| --- | --- |
| 익명화 토큰 포함 (`@이름1@`, `@브랜드명1@`) | 21,992 |
| 발화자 배정 불일치 (성별 대조) | 141 |
| 중복 | 83 |
| 빈 발화 포함 | 1 |
| 발화 6개 미만 | 1 |
| **적격** | **53,782행** |

익명화 토큰이 가장 크다(29%). `extract.py` 는 `source_quote` 를 원문 그대로 저장하고
데이트 코스가 그걸 화면의 추천 이유로 내보낸다 — "@브랜드명1@ 가보고 싶다고 하셨죠"가
그대로 나간다. 그럴듯한 이름으로 채우면 **없던 사실을 만드는 것**이라 행 자체를 뺐다.
남기려면 `--keep-placeholders`.

## 스키마

```jsonc
{
  "id": "msd-000077",
  "source": { "dataset": "nayohan/141_korean_multi_session_dialogue", "rowIndex": 77 },
  "topicType": "시사/사회>타국가이슈(해외)",
  "topicTitle": "전쟁",
  "personas": { "A": ["나는 여자이다.", …], "B": […] },   // 규격 밖. 채점용 참고 자료
  "gapDays": 28,
  "gapSource": "phrase",          // "phrase" = 원문에서 읽음 · "default" = 7일
  "sessions": {
    "session1": { /* AnalysisRequest — fixtures/*.json 과 같은 모양 */ },
    "session2": { /* AnalysisRequest */ }
  },
  "recallHints": [
    { "session2MessageId": 77201, "session1MessageIds": [77105, 77112], "terms": ["정규직", "심사"] }
  ]
}
```

### `recallHints` 는 정답이 아니라 후보다

원본에 재언급 라벨이 없다. **표본 안에서 희귀한 어휘(문서 2% 이하 출현)가 두 세션에
겹치면** 재언급 후보로 잡는다. LLM 을 부르지 않아 비용이 0 이고, `retrieve.py` 가 가져온
기억이 최소한 같은 소재를 가리키는지 자동으로 채점할 수 있다.

한계가 분명하다 — 형태소 분석기를 쓰지 않고 조사·어미를 규칙으로 떼기 때문에
같은 뜻을 다른 낱말로 말한 재언급은 놓치고("소고기"→"고기집"), 우연히 겹친 낱말은
잡는다. **사람이 확인하고 쓴다.**

표본 2,000건 기준 재언급 후보 2,056건 / 케이스 1,042건(52%)이다. 후보가 없는 나머지
48% 는 **음성 케이스**로 쓴다 — 재언급이 없는데 기억을 억지로 끌어오면 그것도 실패다.

## 재생성

```bash
.venv/bin/python -m tools.build_eval_set --download          # 원본 122MB 내려받기 + 빌드
.venv/bin/python -m tools.build_eval_set -n 2000             # 원본이 있으면 빌드만
.venv/bin/python -m tools.build_eval_set -n 0 --out data/eval/msd_full.jsonl   # 전량
```

시드(`--seed 20260816`)가 고정이라 같은 원본이면 같은 표본이 나온다. 원본과 산출물은
`data/eval/` 아래에 두고 **git 에 올리지 않는다**(합쳐서 136MB).

`pyarrow` 가 필요하다. **개발 도구 전용이라 `requirements.txt` 의 워커 런타임 목록과
분리해 두었다** — 배포 이미지에는 들어가지 않는다.

## 검증된 것

- 4,000개 요청(2,000 케이스 × 2 세션) 전부 `AnalysisRequest` 파싱 통과
- 룰 게이트 3종(`check_tone_gate` · `check_date_gate` · `check_concern_gate`)이
  예외 없이 실행됨 — 이 JSON 은 워커에 그대로 넣을 수 있다

## 아직 안 한 것

**평가 하네스.** session1 → `extract.py` → session2 로 `retrieve.py` 를 호출해
`recallHints` 와 대조하는 러너는 만들지 않았다. 케이스마다 LLM 호출이 들어가서
비용·모델을 먼저 정해야 한다 (2,000건 전량이면 추출만 2,000회다).

기억 저장소를 **케이스마다 격리**해야 한다는 점도 걸려 있다. 지금 `extract.py` 는
`data/memories.json` 한 곳에 쌓으므로, 그대로 돌리면 남의 커플 기억이 섞이고
시드 27건이 오염된다.
